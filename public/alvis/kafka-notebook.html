Why Kafka Was Created

MUST KNOW

The problem before Kafka

Before event streaming, systems talked to each other directly — point-to-point. Simple at first:

Application A | v Application B

This works fine for one connection. But real systems need the same data in many places — an order needs to reach shipping, billing, notifications, and analytics all at once. Point-to-point turns into a tangle:

┌── Service A │ Producer ────┼── Service B │ ├── Service C │ └── Service D

Now Application A has to know about, connect to, and manage retries for four different downstream services. That creates:

  • Tight coupling — the producer's code changes every time a new consumer is added.
  • Difficult scaling — each new connection is another direct dependency to manage.
  • Failure propagation — if Service C is slow or down, it can block or crash the sender.
  • Real-time data challenges — polling databases for "what changed" is slow and wasteful.
  • Large data volumes — direct connections don't buffer or absorb traffic spikes.
  • No natural async model — producers and consumers end up waiting on each other.
Interview TipFrame Kafka as solving a coupling problem, not just a "big data" problem. Interviewers love hearing "it decouples producers from consumers" in your own words.

Kafka's answer: put a durable, shared log in the middle. Producers write once; any number of consumers read independently, at their own pace, without the producer knowing or caring who's listening.

Producer ──► Kafka ──┬──► Service A ├──► Service B ├──► Service C └──► Service D

Kafka in the Real World

SHOULD KNOW

Event streaming shows up anywhere something happens once but many parts of a system need to react to it:

Ride-hailing
A ride request needs to reach the driver-matching service, pricing engine, payments, and analytics at the same time.
E-commerce
An order needs to hit inventory, shipping, billing, and recommendation systems.
Banking
Transactions stream into fraud detection, ledgers, and notifications in near real time.
Food delivery
Order status changes need to update the customer app, the restaurant dashboard, and the delivery partner app together.
Real World — illustrative exampleThis is a simplified, illustrative pattern of how ride-hailing style systems commonly use event streaming — not a verified description of any specific company's internal architecture.
Ride Requested ↓ Kafka ↓ ┌────┼─────┬────────┐ ↓ ↓ ↓ ↓ Driver Pricing Payment Analytics

The pattern is always the same: one event, many independent reactions. That's exactly the shape of your Order Tracker project — one order event, consumed independently by the order service and the analytics service.

What is Kafka?

MUST KNOW

Simple version: Kafka is a system that lets one program broadcast "things that happened" and lets many other programs read those things — independently, in order, and even later if they want to replay them.

"Apache Kafka is a distributed event-streaming platform used to publish, store, and process streams of events in real time."

Every word, explained

WordWhat it actually means
DistributedKafka runs across multiple machines (brokers), not just one — so it can handle more data and survive failures.
EventA fact that happened — "order 101 was placed" — not a command or a request.
StreamingEvents keep flowing continuously, not as one-off batches.
PublishProducers write events into Kafka without needing to know who reads them.
StoreKafka keeps events on disk for a retention period — it's a durable log, not just a pipe.
ProcessConsumers (or Kafka Streams) can transform, aggregate, or react to events as they arrive.
Real timeConsumers typically see new events within milliseconds of them being produced.
Remember This — one-liner"Kafka is a distributed, durable log that lets producers publish events once and lets many independent consumers read them in real time — or replay them later."

Core Concepts — Full Architecture

MUST KNOW

Producer | v Kafka Cluster | ├── Broker | └── Topic | ├── Partition 0 ├── Partition 1 └── Partition 2 | v Consumer

Below, every core term gets the same treatment: beginner explanation → analogy → diagram → technical definition → code → interview Q&A → common mistake. Click each to expand.

Producer ▸
Simple explanation

A producer is any program that creates and sends events into Kafka.

Real-world analogy

A news reporter filing a story to the wire service — they don't know (or care) which newspapers will print it.

Technical explanation

A client application that publishes (writes) records to one or more Kafka topics, choosing (or letting Kafka choose) which partition each record lands in.

Code
producer.send("orders", value=order)
Interview Q

What does a producer do in Kafka?

Interview A

"A producer publishes events to a topic. It serializes the data, optionally picks a partition using a key, and sends it to the broker — without needing to know which consumers will read it."

Common MistakeThinking the producer sends directly to a consumer. It never does — it only ever talks to the topic/broker.
Consumer ▸
Simple explanation

A consumer is a program that reads events from a topic.

Real-world analogy

A newspaper subscriber reading the wire feed at their own pace.

Technical explanation

A client that polls a topic (via its assigned partitions) for new records and tracks its position using offsets.

Code
for message in consumer:
    print(message.value)
Interview Q

How does a consumer know where it left off?

Interview A

"It tracks a committed offset per partition — the position of the last record it successfully processed — so on restart it resumes from there instead of re-reading everything."

Common MistakeAssuming consumers "remove" messages when read. They don't — Kafka retains messages for all consumers until the retention period expires.
Topic ▸
Simple explanation

A topic is a named category that events are grouped into — like a folder for one kind of event.

Real-world analogy

A named TV channel — "Sports", "News" — you tune into the one relevant to you.

Technical explanation

A logical stream of records, split into partitions, with its own retention and replication settings.

Diagram
orders payments shipments notifications
Interview Q

What is a Kafka topic?

Interview A

"A topic is a logical, named stream of related events — in my project, the `orders` topic holds every order event, split across 3 partitions."

Common MistakeConfusing a topic with a queue. A topic can be read by many independent consumer groups; a traditional queue message is typically consumed once.
Partition ▸
Simple explanation

A partition is one ordered sub-log inside a topic — splitting the topic so work can be parallelized.

Real-world analogy

Separate lanes on a highway. Cars (events) in the same lane stay in order; cars in different lanes can move independently.

Diagram
Topic ├── Lane 1 (Partition 0) ├── Lane 2 (Partition 1) └── Lane 3 (Partition 2)
Technical explanation

Kafka guarantees order within a partition, not across an entire topic. Partitions are the unit of parallelism — each can be read by only one consumer per consumer group at a time.

Interview Q

Why do partitions matter?

Interview A

"Partitions let a topic scale horizontally — multiple consumers can process different partitions in parallel — while still guaranteeing order for records that share a key."

Common MistakeBelieving Kafka guarantees global ordering across a whole topic. It only guarantees ordering per partition.
Broker ▸
Simple explanation

A broker is one Kafka server — it stores data and serves producer/consumer requests.

Real-world analogy

One warehouse in a chain of warehouses that together form the whole distribution network.

Technical explanation

A broker hosts partitions (as leader or replica), handles reads/writes, and participates in replication.

Interview Q / A

What's a broker? — "A single Kafka server that stores partitions and handles client requests. A Kafka cluster is a group of brokers working together."

Common MistakeThinking "broker" and "cluster" are the same thing — a broker is one node; a cluster is the whole set.
Cluster ▸
Simple explanation

A cluster is a group of brokers working together as one Kafka system.

Real-world analogy

A team of warehouses spread across a city, sharing the load and covering for each other.

Technical explanation

Partitions are distributed across brokers in a cluster; one broker acts as the controller to coordinate metadata.

Interview Q / A

Why use a cluster instead of one broker? — "For scale and fault tolerance — if one broker fails, others still serve the partitions they hold or replicate."

Offset ▸
Simple explanation

An offset is the position number of a record inside a partition.

Real-world analogy

A bookmark in a book — it tells you exactly which page (record) you last read.

Diagram
Partition 0 Offset 0 → Order 101 Offset 1 → Order 102 Offset 2 → Order 103
Interview Q / A

What is an offset? — "A sequential ID for each record within a partition, used by consumers to track and resume their reading position."

Common MistakeThinking committing an offset deletes the message. It doesn't — it only marks progress for that consumer group.
Consumer Group ▸
Simple explanation

A consumer group is a team of consumers that split up the work of reading a topic.

Real-world analogy

A group of cashiers sharing checkout lanes — each lane (partition) is worked by exactly one cashier from the team at a time.

Technical explanation

Kafka assigns each partition to exactly one consumer within a group; this enables parallel processing while different groups can each independently read the whole topic.

Interview Q / A

Why do consumer groups exist? — "To let multiple consumer instances share the work of one topic in parallel, while each group still gets a full, independent copy of the stream."

Replication ▸
Simple explanation

Replication means keeping extra copies of a partition on other brokers, so data survives if one broker dies.

Real-world analogy

Keeping backup copies of an important document in more than one filing cabinet.

Interview Q / A

What does replication factor 3 mean? — "Each partition has 3 copies across 3 different brokers — one leader and two followers — so the data survives up to two broker failures."

Leader & Follower ▸
Simple explanation

For each partition, one broker is the leader (handles all reads/writes); others are followers (just copy the data).

Technical explanation

If the leader fails, an in-sync follower is elected as the new leader automatically — this is how Kafka achieves failover.

Interview Q / A

What happens if the leader broker fails? — "Kafka elects a new leader from the in-sync replicas so the partition keeps serving traffic with minimal disruption."

Topics — Deep Dive

MUST KNOW

A topic is a logical stream or category of related events — think of it as a table name, but for a continuous flow of events rather than static rows.

  • Why topics are needed: they separate unrelated event types so consumers only subscribe to what they care about.
  • Naming: use clear, domain-based names — orders, payments, shipments, notifications.
  • Multiple topics: a real system usually has dozens — one per business event type.
  • Retention: Kafka keeps events for a configured period (e.g. 7 days) or size limit, regardless of whether they've been read.
  • Partitions: every topic is split into 1+ partitions for parallelism (see next section).
Interview TipIf asked "why did you name it `orders`?" — say it maps directly to the business event: "an order was placed." Simple, self-explanatory naming is a good practice to mention.

Partitions — The Most Important Concept

MUST KNOW

orders ├── Partition 0 ├── Partition 1 └── Partition 2

Partition = a separate lane on a highway. Multiple lanes let more cars travel at once (parallelism), but cars within one lane still keep their relative order.

Kafka guarantees ordering within a partition, not across the entire topic.

Concrete example: if orders from customer "Ritik" always use customer as the partition key, all of Ritik's orders land in the same partition and are read in the exact order they were sent. But an order from another customer in a different partition has no ordering guarantee relative to Ritik's orders.

Why partitions exist

  • Parallelism — multiple consumers can work simultaneously.
  • Scalability — more partitions, more brokers can share the load.
  • Ordering — guaranteed only within a single partition.
  • Keys — records with the same key always land in the same partition (via a hash of the key), which is how you get per-entity ordering.

Partition assignment scenarios

3 partitions, 5 consumers (same group)
P0 → Consumer 1 P1 → Consumer 2 P2 → Consumer 3 Consumer 4 → idle Consumer 5 → idle

Only 3 consumers can ever be active — the rest sit idle as standby.

3 partitions, 2 consumers (same group)
P0 → Consumer 1 P1 → Consumer 2 P2 → Consumer 1 (extra)

One consumer handles two partitions — still fully covered, just less parallel.

Common MistakeAdding more consumers than partitions expecting more parallelism. Extra consumers beyond the partition count simply sit idle.

Offsets — Bookmarks in the Log

MUST KNOW

Partition 0 Offset 0 → Order 101 Offset 1 → Order 102 Offset 2 → Order 103 Offset 3 → Order 104

An offset is simply "how far has this consumer group read into this partition." It's per-partition, per-consumer-group.

ActionWhat actually happens
Reading a messageConsumer fetches the record from Kafka — the record still exists in Kafka afterward.
Committing an offsetConsumer tells Kafka "I've finished processing up to here" — this is what's remembered on restart.
Deleting a messageOnly happens via retention expiry (time/size), never because it was read or committed.
  • Consumer restart — resumes from the last committed offset, not from zero.
  • Replay — you can manually reset offsets to re-read old events (great for reprocessing/bug fixes).
  • auto_offset_reset — controls behavior when there's no committed offset yet: "earliest" (read from the start) or "latest" (only read new events).
Interview Tip"Offsets are what make replay possible — that's a key advantage over traditional message queues, where a consumed message is typically gone for good."

Consumer Groups

MUST KNOW

orders topic | ├── Partition 0 ├── Partition 1 └── Partition 2 Consumer Group A ├── Consumer 1 ├── Consumer 2 └── Consumer 3

Consumer groups exist so that many consumer instances can share the work of reading one topic in parallel, instead of every instance reading everything.

  • Rebalancing — when a consumer joins or leaves the group, Kafka automatically re-assigns partitions among the remaining/new consumers.
  • Consumer dies — its partitions are reassigned to other consumers in the group after a rebalance; no data is lost since offsets were already committed.
  • New consumer joins — a rebalance happens and partitions are redistributed to include it.
Classic interview question: "If there are 3 partitions and 5 consumers in one consumer group, how many consumers actively consume?"

Answer: At most 3 — because each partition can be assigned to only one consumer within a consumer group at a time. The other 2 sit idle as standby.

Different consumer groups = independent copies

orders | ├── Order Service Group │ └── Analytics Group

This is exactly your project's shape: the Order Service and Analytics consumers are in different consumer groups, so both receive every event independently — one group's progress never affects the other's.

Producers — In Detail

MUST KNOW

from kafka import KafkaProducer
import json

producer = KafkaProducer(
    bootstrap_servers="localhost:9092",
    value_serializer=lambda v:
        json.dumps(v).encode("utf-8")
)
  • bootstrap_servers — the address(es) used to make first contact with the cluster; Kafka then discovers the rest of the brokers automatically.
  • value_serializer — converts your Python dict into bytes (Kafka only stores bytes) — here, JSON text encoded as UTF-8.
producer.send("orders", value=order)
producer.flush()
  • send() — asynchronously queues the record for delivery and returns immediately (non-blocking).
  • flush() — blocks until all queued records are actually sent, useful before exiting the program.
ADVANCED

acks=0 (fire and forget), acks=1 (leader confirms), acks=all (all in-sync replicas confirm — safest, slightly slower).

ADVANCED

Automatically resends on transient failures — combined with an idempotent producer, this avoids duplicate writes.

ADVANCED

Producers group multiple records into one network request for efficiency, controlled by batch.size and linger.ms.

ADVANCED

Compresses batches (gzip, snappy, lz4, zstd) to cut network and storage cost.

SHOULD KNOW

A key (e.g. customer) determines which partition a record lands in — same key, same partition, preserving per-key order.

Consumers — In Detail

MUST KNOW

from kafka import KafkaConsumer
import json

consumer = KafkaConsumer(
    "orders",
    bootstrap_servers="localhost:9092",
    group_id="analytics-group",
    auto_offset_reset="earliest",
    enable_auto_commit=True,
    value_deserializer=lambda x:
        json.loads(x.decode("utf-8"))
)

for message in consumer:
    print(message.value)
  • group_id — which consumer group this instance belongs to; determines partition sharing.
  • auto_offset_reset — what to do with no committed offset: earliest or latest.
  • enable_auto_commit — whether offsets commit automatically on an interval (simpler, slightly less safe) vs. manual commits (more control, avoids losing progress on crash mid-batch).
  • value_deserializer — converts bytes back into a Python object.
  • Polling — the for message in consumer loop continuously polls Kafka for new records.
Interview TipMention that your project uses enable_auto_commit=True for simplicity, but you know manual commits give more control in production — this shows depth without overclaiming.

Brokers & Kafka Cluster

SHOULD KNOW

Kafka Cluster ├── Broker 1 ├── Broker 2 └── Broker 3

Multiple brokers share the partitions of every topic across the cluster. For a partition:

Partition 0 Leader → Broker 1 Replica → Broker 2 Replica → Broker 3

If Broker 1 fails: Kafka elects a new leader (say Broker 2) from the in-sync replicas. Producers and consumers reconnect to the new leader automatically — the partition keeps serving with a brief blip, not an outage.

My project uses a single local broker (no multi-broker cluster) — fine for learning, but production systems typically run 3+ brokers for real fault tolerance.

Replication

MUST KNOW

Replication means keeping copies of partitions on multiple brokers.

Replication Factor = 3 Broker 1 → Leader Broker 2 → Replica Broker 3 → Replica

More replicas = more fault tolerance, at the cost of extra storage and network traffic to keep replicas in sync.

My project: Replication Factor = 1

Acceptable for a local, single-broker learning project — there's only one broker, so there's nowhere to put a second copy anyway. Not acceptable for production, where a single broker failure would mean data loss.

Exact interview answer to memorize:
"I used replication factor 1 because my project runs locally with a single Docker Kafka broker. For production I would use multiple brokers and a replication factor of at least 3 for fault tolerance."

ZooKeeper vs KRaft

SHOULD KNOW

Older Kafka
Kafka + ZooKeeper

ZooKeeper tracked cluster metadata — broker membership, topic configs, and controller election — as a separate system Kafka depended on.

Modern Kafka
Kafka + KRaft

KRaft (Kafka Raft) moves that metadata management inside Kafka itself, removing the ZooKeeper dependency entirely.

Why the move: one less system to operate, faster controller failover, and simpler deployments.

Interview Tip"If asked about modern Kafka, mention KRaft" — say something like: "Newer Kafka versions use KRaft mode instead of ZooKeeper, which simplifies operations by removing a separate coordination service."

Docker + Kafka

SHOULD KNOW

Docker | └── Kafka Broker | └── orders topic

Docker packages Kafka (and its dependencies) into a container, so you don't need to manually install and configure a broker on your machine — one command spins up a working environment.

docker compose up -d
  • Ports — the broker is exposed on localhost:9092, the standard Kafka port, so local Python scripts can connect to it directly.
  • Container networking — containers can talk to each other by service name inside Docker's network, while your host machine reaches them via mapped ports.
  • Why Docker helps — reproducible setup, easy teardown/restart, and no messy local installs.

My Project — Kafka Order Tracker

MUST KNOW — this is your interview centerpiece

Producer | v orders Topic / | \ / | \ P0 P1 P2 \ | / \ | / Consumers / \ / \ Order Consumer Analytics Consumer | ├── Total Orders └── Total Revenue

Step-by-step flow of one order

  1. User (or a script) enters an order.
  2. Producer receives the order data.
  3. Producer builds a JSON event, e.g. {"order_id":"101","customer":"Ritik","amount":15000,"region":"north"}.
  4. Producer serializes the event (JSON → UTF‑8 bytes).
  5. Producer sends the event to the orders topic on the broker.
  6. Kafka appends the event to a partition and stores it durably on disk.
  7. The event is assigned a partition (by key hash, or round-robin if no key).
  8. Both consumer groups — Order Service and Analytics — independently poll and read the event.
  9. The Order Consumer processes it (e.g. logs/handles the order).
  10. The Analytics Consumer updates its running totals: Total Orders and Total Revenue.
Trace this exact eventOrder 101 (Ritik, ₹15,000, north) → serialized to bytes → sent to `orders` → landed in one partition, say Partition 1 → both consumer groups poll Partition 1 → Order Consumer marks it received → Analytics Consumer adds ₹15,000 to revenue and +1 to order count.
Interview TipAlways describe your project as demonstrating the publish/subscribe and producer/consumer patterns with independent consumer groups — that's the vocabulary interviewers are listening for.

Project Code Walkthrough

MUST KNOW

producer.py

Purpose: reads order data and publishes it to the "orders" topic.
from kafka import KafkaProducer
import json, time

producer = KafkaProducer(
    bootstrap_servers="localhost:9092",
    value_serializer=lambda v: json.dumps(v).encode("utf-8")
)

order = {
    "order_id": "101",
    "customer": "Ritik",
    "amount": 15000,
    "region": "north"
}

producer.send("orders", key=order["customer"].encode(), value=order)
producer.flush()
print("Order sent:", order)

Line by line: connects to the local broker → defines how Python dicts become bytes → builds one order event → sends it, using the customer name as the partition key (so all of one customer's orders land in the same partition) → flushes to guarantee delivery before exiting.

Interview question"Why did you use `customer` as the key?" → "So all events from the same customer are ordered relative to each other, since Kafka only guarantees order within a partition."

order_consumer.py

Purpose: represents the "order service" — reacts to new orders (e.g., logs/confirms them).
from kafka import KafkaConsumer
import json

consumer = KafkaConsumer(
    "orders",
    bootstrap_servers="localhost:9092",
    group_id="order-service-group",
    auto_offset_reset="earliest",
    value_deserializer=lambda v: json.loads(v.decode("utf-8"))
)

for msg in consumer:
    order = msg.value
    print(f"[Order Service] Processing order {order['order_id']} for {order['customer']}")

Line by line: subscribes to orders under its own consumer group → reads from the earliest offset if it has no committed position yet → deserializes bytes back to a dict → prints/handles the order.

analytics_consumer.py

Purpose: independently tracks running totals (orders count, revenue) for the same event stream.
from kafka import KafkaConsumer
import json

consumer = KafkaConsumer(
    "orders",
    bootstrap_servers="localhost:9092",
    group_id="analytics-group",
    auto_offset_reset="earliest",
    value_deserializer=lambda v: json.loads(v.decode("utf-8"))
)

total_orders = 0
total_revenue = 0

for msg in consumer:
    order = msg.value
    total_orders += 1
    total_revenue += order["amount"]
    print(f"Orders: {total_orders} | Revenue: ₹{total_revenue}")

Line by line: uses a different group_id than the order consumer — this is exactly why it receives every event independently, rather than sharing partitions with the order service. It keeps running totals in memory as each event arrives.

Common MistakePutting both consumers in the same `group_id`. That would split the partitions between them instead of giving each a full copy of the stream.

docker-compose.yml

Purpose: spins up a local single-broker Kafka cluster.
services:
  kafka:
    image: bitnami/kafka:latest
    ports:
      - "9092:9092"
    environment:
      - KAFKA_CFG_NODE_ID=0
      - KAFKA_CFG_PROCESS_ROLES=controller,broker
      - KAFKA_CFG_LISTENERS=PLAINTEXT://:9092,CONTROLLER://:9093
      - KAFKA_CFG_ADVERTISED_LISTENERS=PLAINTEXT://localhost:9092
      - KAFKA_CFG_CONTROLLER_QUORUM_VOTERS=0@kafka:9093
      - KAFKA_CFG_CONTROLLER_LISTENER_NAMES=CONTROLLER

Line by line: pulls a Kafka image → maps container port 9092 to the host so local Python can connect → configures a single-node KRaft broker (no separate ZooKeeper needed) — good to mention that you're aware this is a modern KRaft-based setup.

Real-Time Analytics

SHOULD KNOW

Order 1 → ₹50,000 Order 2 → ₹80,000 Order 3 → ₹74,900 Total Orders = 3 Total Revenue = ₹204,900

Each event updates the in-memory counters as it arrives — this is the simplest possible form of stream processing: a running aggregate.

Question to expect: "What happens if the analytics consumer restarts?"
Honest answer: "In its current form, the in-memory totals reset to zero — that's a real limitation. In production I'd persist state so restarts don't lose the running totals."

ADVANCED — how a production system would fix this:

  • Database — persist running totals so they survive restarts.
  • Redis — fast in-memory store for counters, with optional persistence.
  • Kafka Streams — a stream-processing library with built-in, fault-tolerant state stores.
  • Materialized state / checkpointing — periodically snapshot aggregate state so recovery doesn't require replaying the entire topic from scratch.

Kafka vs RabbitMQ

SHOULD KNOW

AspectKafkaRabbitMQ
PurposeDistributed event streaming / durable logTraditional message broker for routing
ArchitecturePartitioned log, pull-based consumersExchanges + queues, push-based delivery
StorageRetains events on disk for a retention windowTypically removes messages once consumed/acked
PartitionsYes — core to scaling and orderingNo native concept; scaling is via multiple queues
Consumer groupsBuilt-in, partition-based sharingCompeting consumers on a queue
ReplayYes — reset offsets and re-read historyGenerally no — consumed messages are gone
ThroughputVery high, optimized for large volumesHigh, but typically lower than Kafka at scale
RoutingSimple — topic-basedRich routing (exchanges, bindings, patterns)
Typical use caseEvent streaming, analytics pipelines, logsTask queues, complex routing, RPC-style messaging
Interview answer: "Kafka is primarily a distributed event-streaming platform designed for high-throughput, durable, replayable streams, while RabbitMQ is traditionally a message broker focused on routing messages between producers and consumers. Neither is universally better — it depends on whether you need replay/streaming semantics or flexible routing/queueing semantics."

Kafka vs REST API

SHOULD KNOW

REST
Client → Server ↓ Response
Kafka
Producer → Kafka → Consumer
  • Synchronous vs asynchronous — REST typically waits for a response; Kafka producers fire events without waiting for a consumer.
  • Request/response vs event streaming — REST answers "give me X now"; Kafka broadcasts "X happened."
  • Coupling — REST clients need to know the server's address; Kafka producers don't need to know who's consuming.
  • Buffering — Kafka naturally absorbs traffic spikes since it's a durable log; REST servers can get overwhelmed directly.
  • Replay — Kafka lets you re-read history; REST has no concept of "replay a past request."
  • Real-time processing — Kafka fits continuous streams; REST fits one-off queries/commands.

When to use which: use REST for "fetch me this specific record right now" (e.g. get an order's current status); use Kafka for "notify everyone whenever an order happens" (e.g. your Order Tracker's event flow).

"Explain Kafka in 30 Seconds"

"Kafka is a distributed event-streaming platform. Producers publish events to topics, topics are divided into partitions for scalability and ordering, and consumers read those events. Consumer groups allow multiple consumers to process partitions in parallel. Kafka also provides durable storage and replay, making it useful for real-time data pipelines and event-driven systems."

Two independent consumers read from that same topic under different consumer groups: an order consumer that represents the order-processing service, and an analytics consumer that calculates real-time metrics — total orders and total revenue — as each event arrives. The project is small, but it demonstrates the core ideas behind Kafka: producers and consumers, topics and partitions, consumer groups, offsets, and real-time, event-driven processing — the same patterns that power production systems at much larger scale."
