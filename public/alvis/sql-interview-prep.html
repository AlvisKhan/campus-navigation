TABLE 01

SELECT Fundamentals

EASY

Almost every interview opens here to check baseline fluency. The clause order you write is not the order SQL executes — that mismatch is a favorite trick question.

Logical execution order

execution ordernot write order
FROM  >  WHERE  >  GROUP BY  >  HAVING  >  SELECT  >  DISTINCT  >  ORDER BY  >  LIMIT

This is why you can't reference a SELECT alias inside WHERE (WHERE runs before SELECT), but you can use it in ORDER BY (which runs last).

Basic shape

queryemployees
SELECT first_name, last_name, salary
FROM employees
WHERE department = 'Engineering'
ORDER BY salary DESC
LIMIT 5;
iDISTINCT applies to the whole selected row, not one column at a time — SELECT DISTINCT a, b removes rows where both a and b repeat together, not each column independently.

Common gotchas

Why does SELECT name, COUNT(*) without GROUP BY fail?+

Mixing an aggregate (COUNT(*)) with a non-aggregated column requires that column to appear in GROUP BY, otherwise SQL can't decide which single name to show per aggregated group. MySQL is permissive by default in some modes; Postgres and SQL Server will reject it outright.

NULL comparisons: why does WHERE age != NULL return nothing?+

NULL means "unknown," so any comparison to it (=, !=, >) evaluates to unknown, not true. Use IS NULL / IS NOT NULL instead.

Filtering & Operators

EASY

Interviewers probe whether you reach for the right operator instead of over-engineering with nested CASE logic.

pattern matching & ranges
SELECT * FROM orders
WHERE status IN ('shipped', 'delivered')
  AND order_total BETWEEN 50 AND 500
  AND customer_email LIKE '%@gmail.com'
  AND cancelled_at IS NULL;
OperatorUse it forWatch out for
IN (...)matching a set of discrete valueslarge lists are slower than a JOIN to a temp table
BETWEENinclusive numeric/date rangesinclusive on both ends — off-by-one bugs
LIKE / ILIKEpattern matching with % and _leading % ('%foo') can't use a standard index
COALESCEfirst non-null value in a listevaluate types match across arguments
CASE WHENinline conditional logicalways add an ELSE, or you'll get silent NULLs

Three-valued logic (the trap)

!SQL logic isn't just TRUE/FALSE — it's TRUE / FALSE / UNKNOWN. NULL AND FALSE is FALSE, but NULL AND TRUE is UNKNOWN, and a WHERE clause only keeps rows that evaluate to TRUE. This trips people up constantly with NOT IN subqueries that contain a NULL — the whole clause silently returns zero rows.

How to explain it in an interview

          
    
            
  • INNER JOIN — only rows with a match on both sides. Carol (no dept) and HR (no employees) both disappear.
    • 
            
  • LEFT JOIN — every row from the left table, matched columns filled with NULL when there's no match. Carol stays, HR doesn't appear.
    • 
            
  • RIGHT JOIN — mirror of LEFT; every department shows even with zero employees.
    • 
            
  • FULL OUTER JOIN — union of LEFT and RIGHT; nothing gets dropped.
    • 
            
  • CROSS JOIN — cartesian product, every row × every row, no ON clause. 4 employees × 3 departments = 12 rows.
    • 
            
  • SELF JOIN — a table joined to itself, typically to compare rows or walk a hierarchy (e.g. employee → manager).

          TABLE 04
          
GROUP BY & Aggregates

          CORE 
        

        

          
The recurring test: do you know HAVING filters groups while WHERE filters rows, before grouping happens.


          

            
departments with >3 highly-paid engineers

            
SELECT department, COUNT(*) AS headcount, AVG(salary) AS avg_salary
FROM employees
WHERE salary > 80000          -- filters rows, before grouping
GROUP BY department
HAVING COUNT(*) > 3       -- filters groups, after aggregating
ORDER BY avg_salary DESC;

          


          

            
FunctionIgnores NULLs?Notes

            
              
COUNT(col)yesCOUNT(*) counts rows regardless of NULLs

              
SUM / AVGyesAVG divides by the count of non-null values, not total rows

              
MIN / MAXyesworks on text and dates too, not just numbers

              
GROUP_CONCAT / STRING_AGGyessyntax and name differ by database engine

            
          


          
iRule of thumb interviewers listen for: "WHERE happens before the grouping, HAVING happens after." Say it exactly like that and most follow-ups resolve themselves.


          
        

      


      
      

        

          TABLE 05
          
Subqueries & CTEs

          MEDIUM 
        

        

          
Being able to rewrite a nested subquery as a CTE — and explain why you'd want to — is a strong signal of real experience.


          
Correlated vs. non-correlated

          

            
non-correlated — runs once

            
SELECT name, salary FROM employees
WHERE salary > (SELECT AVG(salary) FROM employees);

          

          

            
correlated — runs once per outer row

            
SELECT e.name, e.salary FROM employees e
WHERE e.salary > (
  SELECT AVG(e2.salary) FROM employees e2
  WHERE e2.department = e.department  -- references outer row
);

          


          
CTEs read top-to-bottom like a recipe

          

            
readable multi-step logic

            
WITH dept_avg AS (
  SELECT department, AVG(salary) AS avg_salary
  FROM employees
  GROUP BY department
)
SELECT e.name, e.department, e.salary, d.avg_salary
FROM employees e
JOIN dept_avg d ON e.department = d.department
WHERE e.salary > d.avg_salary;

          


          
Recursive CTE (hierarchies)

          

            
employee → manager chain

            
WITH RECURSIVE org_chart AS (
  SELECT id, name, manager_id, 1 AS depth
  FROM employees WHERE manager_id IS NULL   -- anchor
  UNION ALL
  SELECT e.id, e.name, e.manager_id, o.depth + 1
  FROM employees e
  JOIN org_chart o ON e.manager_id = o.id      -- recursive step
)
SELECT * FROM org_chart ORDER BY depth;

          


          

            When would you pick a subquery over a JOIN?+
            
When you only need a scalar or existence check (EXISTS, an aggregate for filtering) and don't need columns from the second table in your final result — a subquery keeps intent clearer and sometimes lets the optimizer short-circuit early. If you need columns from both tables side by side, a JOIN is usually the right call.

          


          
        

      


      
      

        

          TABLE 06
          
Window Functions

          HARD 
        

        

          
What separates "knows SQL" from "used SQL professionally." Window functions calculate across a set of rows related to the current row without collapsing them into one — unlike GROUP BY.


          

            
rank employees by salary, per department

            
SELECT name, department, salary,
  RANK()       OVER (PARTITION BY department ORDER BY salary DESC) AS rnk,
  DENSE_RANK() OVER (PARTITION BY department ORDER BY salary DESC) AS dense_rnk,
  ROW_NUMBER() OVER (PARTITION BY department ORDER BY salary DESC) AS rn
FROM employees;

          


          

            
FunctionTies behave like

            
              
ROW_NUMBER()always unique, breaks ties arbitrarily (1,2,3,4)

              
RANK()ties share a rank, next rank skips (1,1,3,4)

              
DENSE_RANK()ties share a rank, no gap (1,1,2,3)

            
          


          
Running totals & comparisons to neighboring rows

          

            
running total + month-over-month diff

            
SELECT month, revenue,
  SUM(revenue) OVER (ORDER BY month) AS running_total,
  revenue - LAG(revenue) OVER (ORDER BY month) AS mom_change
FROM monthly_sales;

          


          
iLAG looks at the previous row, LEAD looks at the next row. Both take an optional offset and default value: LAG(revenue, 1, 0).

          
!Window functions run after WHERE/GROUP BY/HAVING but before ORDER BY and LIMIT — so you can't filter on a window function's result directly in WHERE. Wrap the query in a CTE or subquery and filter in the outer layer.


          
        

      


      
      

        

          TABLE 07
          
Set Operations

          MEDIUM 
        

        

          
Combine full result sets vertically (same column count/types) rather than side by side like a JOIN.

          

            
customers who bought in-store OR online

            
SELECT customer_id FROM in_store_orders
UNION
SELECT customer_id FROM online_orders;

          

          

            
OperatorBehavior

            
              
UNIONcombines & removes duplicate rows

              
UNION ALLcombines & keeps duplicates — cheaper, no dedup pass

              
INTERSECTrows present in both result sets

              
EXCEPT / MINUSrows in the first set but not the second

            
          

          
iPrefer UNION ALL unless you specifically need dedup — the duplicate-elimination pass in plain UNION requires a sort/hash over the entire combined set.

          
        

      


      
      

        

          TABLE 08
          
Indexes & Query Optimization

          HARD 
        

        

          
This is where "wrote SQL" turns into "understands what the database is actually doing." Expect at least one question on EXPLAIN output.


          
How a B-tree index helps

          
An index is a sorted side-structure mapping column values to row locations. Without one, a filter on a large table forces a full table scan — the engine reads every row. With one, it can binary-search straight to matching rows.


          

            
reading EXPLAIN output

            
EXPLAIN SELECT * FROM orders WHERE customer_id = 4521;

-- Seq Scan on orders   (no usable index — bad on a big table)
-- Index Scan using orders_customer_id_idx  (good)

          


          

            
Index typeBest for

            
              
B-treeequality & range queries (=, >, <, BETWEEN) — the default

              
Hashpure equality lookups only, no ranges

              
Composite (multi-column)queries filtering on multiple columns together — column order matters

              
Covering indexincludes every column the query needs, avoiding a lookup back to the table

            
          


          

            Why can too many indexes hurt performance?+
            
Every INSERT/UPDATE/DELETE must also update every index on that table, so write-heavy tables pay a real cost per extra index. Indexes also consume disk and memory. The trade-off is always read speed vs. write speed vs. storage.

          

          

            Why doesn't WHERE UPPER(email) = 'X@Y.COM' use a normal index on email?+
            
Wrapping an indexed column in a function computes a new value the index wasn't built on, so the engine can't binary-search it — this forces a full scan. Fix it with a functional/expression index on UPPER(email), or store a normalized column.

          


          
        

      


      
      

        

          TABLE 09
          
Normalization

          MEDIUM 
        

        

          
Design questions test whether you can spot redundancy that will cause update anomalies later — not whether you've memorized textbook definitions.


          

            
FormRuleFixes

            
              
1NFatomic columns, no repeating groupsa "phone_numbers" column storing a comma list

              
2NF1NF + no partial dependency on a composite keya column depending on only part of a multi-column key

              
3NF2NF + no transitive dependencya non-key column depending on another non-key column

              
BCNFevery determinant is a candidate keyedge cases 3NF misses with overlapping candidate keys

            
          


          
A 3NF violation, made concrete

          

            
bad — zip_code determines city, not employee_id

            
employees(id, name, zip_code, city, state)
-- city and state are transitively dependent on zip_code, not on id.
-- update the zip and city/state can drift out of sync.

          

          

            
fixed — split into two tables

            
employees(id, name, zip_code)
zip_codes(zip_code, city, state)

          


          
iGood talking point: normalization removes redundancy and prevents update anomalies but adds JOINs. Denormalization is a deliberate trade — often used in read-heavy analytics tables — accepting redundancy for fewer joins and faster reads.


          
        

      


      
      

        

          TABLE 10
          
Transactions & ACID

          MEDIUM 
        

        

          

            

              
A — Atomicity

              
All statements in a transaction succeed, or none do. A crash mid-transfer never leaves money debited from one account without crediting another.

            

            

              
C — Consistency

              
A transaction moves the database from one valid state to another — constraints, triggers, and cascades all still hold afterward.

            

            

              
I — Isolation

              
Concurrent transactions don't see each other's uncommitted changes. How strictly this holds is tunable — that's isolation levels, below.

            

            

              
D — Durability

              
Once committed, a change survives a crash — typically guaranteed by a write-ahead log flushed to disk.

            

          


          
Isolation levels, weakest to strongest

          

            
LevelAllows

            
              
Read Uncommitteddirty reads, non-repeatable reads, phantom reads

              
Read Committednon-repeatable reads, phantom reads (default in Postgres/Oracle)

              
Repeatable Readphantom reads only (default in MySQL/InnoDB)

              
Serializablenone — transactions behave as if run one at a time

            
          


          

            
a transfer, wrapped safely

            
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;   -- or ROLLBACK if either UPDATE failed

          


          
!Higher isolation reduces anomalies but increases locking/contention and lowers throughput — this trade-off question comes up almost every time ACID does.


          
        

      


      
      

        

          TABLE 11
          
Classic Interview Queries

          CORE 
        

        

          
These specific puzzles get reused across companies almost verbatim. Know the pattern, not just the answer.


          

            Find the Nth highest salary+
            

              
The robust, engine-agnostic way handles ties correctly with DENSE_RANK:

              
2nd highest, ties collapse to one rank
SELECT salary FROM (
  SELECT salary, DENSE_RANK() OVER (ORDER BY salary DESC) AS rnk
  FROM employees
) ranked
WHERE rnk = 2;

              
The classic (older) alternative, without window functions:

              
OFFSET/LIMIT trick
SELECT DISTINCT salary FROM employees
ORDER BY salary DESC
LIMIT 1 OFFSET 1;

            

          


          

            Find duplicate rows+
            

              
emails appearing more than once
SELECT email, COUNT(*) AS occurrences
FROM users
GROUP BY email
HAVING COUNT(*) > 1;

            

          


          

            Delete duplicate rows, keeping one+
            

              
keep the lowest id per duplicate email
DELETE FROM users
WHERE id NOT IN (
  SELECT MIN(id) FROM users GROUP BY email
);

            

          


          

            Employees earning more than their manager+
            

              
A textbook self-join:

              
self join on manager_id
SELECT e.name AS employee, m.name AS manager
FROM employees e
JOIN employees m ON e.manager_id = m.id
WHERE e.salary > m.salary;

            

          


          

            Find consecutive occurrences (e.g. 3+ days in a row of logins)+
            

              
The "gaps and islands" pattern: subtract a ROW_NUMBER from the date to give every consecutive run the same constant value, then group on it.

              
gaps & islands
WITH numbered AS (
  SELECT user_id, login_date,
    login_date - (ROW_NUMBER() OVER (
      PARTITION BY user_id ORDER BY login_date
    )) * INTERVAL '1 day' AS grp
  FROM logins
)
SELECT user_id, MIN(login_date) AS streak_start, COUNT(*) AS streak_len
FROM numbered
GROUP BY user_id, grp
HAVING COUNT(*) >= 3;
