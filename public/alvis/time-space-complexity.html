01 · Foundations

Why we measure algorithms at all

Two pieces of code can solve the exact same problem and produce the exact same output, yet one finishes in a blink and the other locks up a machine. Complexity analysis is how we predict which one before we ever run either — by counting how the amount of work (time) or memory (space) grows as the input grows, independent of the specific computer running it.

This matters because your laptop is irrelevant to the analysis. A function that is O(n²) will eventually lose to an O(n log n) function on any hardware, once n is large enough — it's a statement about the shape of growth, not a stopwatch reading.

Mental model Think of complexity as answering one question: "If I double the input size, what happens to the work?" Does it stay the same? Double? Quadruple? Explode? That single question is the seed of everything below.
02 · Foundations

Big‑O, Big‑Ω, and Big‑Θ

These three notations describe bounds on a function's growth. In interviews, "complexity" almost always means Big‑O (the upper bound / worst case ceiling), but knowing all three makes you sound — and think — like someone who actually understands the math, not just the vocabulary.

OBig‑O (upper bound)

"Grows no faster than this." A guaranteed ceiling — the algorithm will never be worse than this, for large enough n. This is what we use to describe worst‑case performance.

ΩBig‑Omega (lower bound)

"Grows no slower than this." A guaranteed floor — describes the best‑case or a minimum amount of unavoidable work.

ΘBig‑Theta (tight bound)

Upper and lower bound match — the algorithm's growth is exactly this rate, not just bounded by it.

Formally: f(n) = O(g(n)) means there exist positive constants c and n₀ such that f(n) ≤ c·g(n) for all n ≥ n₀. In plain English: past some point, a constant multiple of g(n) always sits above f(n).

Growth curves side‑by‑side (n = 0 → 18)

Standard view: notice how O(2ⁿ) and O(n²) start low at small n and then explode upwards out of the chart, completely dwarfing linear and logarithmic growth. Click any legend item to toggle that curve.

03 · Foundations

The simplification rules

We never report exact operation counts — we report the shape of growth. Four rules get you there every time.

  • 1. Drop constants

    O(2n), O(n + 5), and O(n/2) are all just O(n). A constant factor doesn't change the growth shape — doubling n still roughly doubles the work either way.

  • 2. Drop lower‑order terms

    O(n² + n + 1) becomes O(n²). As n grows large, the n² term completely dwarfs the rest — at n = 10,000, n² is 100 million while n is only 10,000.

  • 3. Different inputs get different variables

    A function looping over array A (size n) and then array B (size m) is O(n + m), not O(n). Never assume two inputs are the same size unless told so.

  • 4. Multiply nested, add sequential

    Loops inside loops multiply: a loop of n containing a loop of m is O(n·m). Loops that run one after another add: O(n) + O(m) = O(n + m).

    • rules.cpp
    // Sequential  →  ADD   →  O(n + m)
for (int i = 0; i < n; i++) { doWork(i); }
for (int j = 0; j < m; j++) { doWork(j); }

// Nested      →  MULTIPLY → O(n * m)
for (int i = 0; i < n; i++)
    for (int j = 0; j < m; j++)
        doWork(i, j);
    04 · Core skill

    Analyzing loops (the workhorse skill)

    Nearly every interview complexity question reduces to "how many times does this loop body actually run?" Master these six patterns and you can compose them to handle almost anything.

    4.1 — Single loop, constant step

    single_loop.cppO(n)
    for (int i = 0; i < n; i++) {
    std::cout << i; // runs exactly n times
}

    The loop variable moves by a fixed amount (+1), so the number of iterations is directly proportional to n.

    4.2 — Loop with a bigger constant step

    step_loop.cppO(n)
    for (int i = 0; i < n; i += 2) {
    std::cout << i; // runs n/2 times
}

    n/2 is still O(n) — rule #1, drop the constant. The step size changes the constant factor, not the growth shape.

    4.3 — Nested independent loops

    nested_independent.cppO(n²)
    for (int i = 0; i < n; i++)
    for (int j = 0; j < n; j++)
        std::cout << i * j; // runs n * n times

    Watch the n × n grid get visited

    Cells visited: 0
    Total cells: 100
    Each cell = one loop-body execution. The grid fills at a rate of n² — this is what "quadratic" looks like in the flesh.

    4.4 — Nested dependent loops (a very common trap)

    nested_dependent.cppO(n²)
    for (int i = 0; i < n; i++)
    for (int j = i; j < n; j++) // inner loop shrinks
        std::cout << i * j;

    The inner loop runs n, n-1, n-2, ... 1 times as i increases. Summed, that's n + (n-1) + ... + 1 = n(n+1)/2. Drop the constant and lower‑order term: still O(n²). The pattern to remember: any triangular iteration (inner bound depends linearly on outer index) is still quadratic — it just has a smaller constant (½) than a full square.

    4.5 — Logarithmic loop (multiplicative step)

    log_loop.cppO(log n)
    for (int i = 1; i < n; i *= 2) {
    std::cout << i; // i: 1, 2, 4, 8, 16 ... 
}

    The moment you see the loop variable being multiplied or divided each iteration (instead of added/subtracted), think log n. The question "how many times can you double 1 before passing n?" is literally the definition of log₂ n.

    Doubling i until it passes n (log growth)

    Steps taken so far: 0 — for n = 64, only log₂(64) = 6 steps are ever needed.

    4.6 — Loop with recursive‑like halving (binary search)

    binary_search.cppO(log n)
    int binarySearch(std::vector<int>& arr, int target) {
    int lo = 0, hi = arr.size() - 1;
    while (lo <= hi) {
        int mid = lo + (hi - lo) / 2;
        if (arr[mid] == target) return mid;
        else if (arr[mid] < target) lo = mid + 1;
        else hi = mid - 1;
    }
    return -1;
}

    Each iteration discards half the remaining search space. That halving pattern is the other big log n signal — whenever the problem size shrinks by a fixed fraction each step (not a fixed amount), you're looking at logarithmic time.

    Pattern you see in codeWhat to thinkTypical complexity
    i++ or i--Linear stepO(n)
    i += k for constant kStill linear, smaller constantO(n)
    i *= 2 / i /= 2Multiplicative stepO(log n)
    Inner loop bound depends on outer index (j = i)Triangular iterationO(n²)
    Loop + halving inside (e.g. binary search inside a loop)Multiply the piecesO(n log n)
    Recursion branching into 2 calls per level, full depth nExponential branchingO(2ⁿ)

    06 · Core skill

    Recursion & recurrence relations

    Recursive code can't be "counted" by staring at a single loop — you need to express the running time as a function of itself (a recurrence) and then solve it.

    6.1 — Write the recurrence

    Ask two questions: (1) how many subproblems does one call spawn, and how much smaller is each? (2) how much non‑recursive work happens per call?

    factorial.cppO(n)
    int factorial(int n) {
    if (n <= 1) return 1;      // base case: O(1)
    return n * factorial(n - 1); // 1 subcall, size n-1
}
// T(n) = T(n-1) + O(1)  →  T(n) = O(n)
    fibonacci_naive.cppO(2ⁿ)
    int fib(int n) {
    if (n <= 1) return n;
    return fib(n - 1) + fib(n - 2); // 2 subcalls, size n-1
}
// T(n) = 2T(n-1) + O(1)  →  T(n) = O(2^n)

    Recursion tree — fib(4) branching into O(2ⁿ) calls

    Every call that isn't a base case spawns two more. The tree's node count roughly doubles per level — that explosion is O(2ⁿ). Memoizing (caching results) collapses this to O(n) by never recomputing a subproblem.

    6.2 — Merge sort: the classic divide‑and‑conquer

    merge_sort.cppO(n log n)
    void mergeSort(std::vector<int>& a, int l, int r) {
    if (l >= r) return;
    int mid = l + (r - l) / 2;
    mergeSort(a, l, mid);       // T(n/2)
    mergeSort(a, mid + 1, r);   // T(n/2)
    merge(a, l, mid, r);        // O(n) to merge
}
// T(n) = 2T(n/2) + O(n)  →  T(n) = O(n log n)

    Why 2T(n/2) + O(n) becomes O(n log n)

    Every level of the tree does O(n) total work (merge operations sum to cn per row, plus O(n) at the base leaves). Halving n takes log₂ n = 3 divisions, giving log₂ n + 1 = 4 levels total. Total work = (log n + 1) × O(n) = O(n log n).

    6.3 — The Master Theorem (shortcut for divide & conquer)

    For recurrences of the form T(n) = a·T(n/b) + O(nd) — a subproblems, each of size n/b, plus O(nd) work to combine — compare d against logb a:

    ConditionResultExample
    d < log_b(a)O(nlog_b a)Naive recursive matrix mult: T(n)=8T(n/2)+O(n²) → O(n³)
    d = log_b(a)O(nd log n)Merge sort: T(n)=2T(n/2)+O(n) → O(n log n)
    d > log_b(a)O(nd)T(n)=2T(n/2)+O(n²) → O(n²)
    Interview‑speed trickYou rarely need the full theorem. Just remember the three named shapes: T(n)=T(n/2)+O(1) → O(log n) (binary search); T(n)=2T(n/2)+O(n) → O(n log n) (merge sort); T(n)=2T(n-1)+O(1) → O(2ⁿ) (naive recursion tree, subtracting not dividing).
    07 · Core skill

    Space complexity

    Space complexity counts extra memory an algorithm needs, as a function of n — not counting the input itself. Two sources are commonly missed by people who are otherwise fine at time complexity: auxiliary data structures, and the call stack that recursion silently builds.

    7.1 — Iterative: O(1) space

    sum_iterative.cppO(1) space
    int sum(std::vector<int>& a) {
    int total = 0;             // one variable, regardless of n
    for (int x : a) total += x;
    return total;
}

    7.2 — Recursive: O(n) space (the hidden call stack)

    sum_recursive.cppO(n) space
    int sum(std::vector<int>& a, int i) {
    if (i == a.size()) return 0;
    return a[i] + sum(a, i + 1); // n stack frames alive at once
}

    Even though this does the exact same work as 7.1, it needs O(n) space, because n stack frames are stacked up waiting for their recursive call to return before they can add and return. Every unreturned recursive call sits in memory. This is precisely why deep recursion risks a stack overflow, and why "just make it recursive" is not free.

    7.3 — Auxiliary array: O(n) space

    reverse_new_array.cppO(n) space
    std::vector<int> reversed(std::vector<int>& a) {
    std::vector<int> out(a.size());   // new array of size n
    for (int i = 0; i < a.size(); i++)
        out[i] = a[a.size() - 1 - i];
    return out;
}
// compare: reversing a[] IN PLACE with two pointers is O(1) space
    Quick checklist for space Count: (a) any array/vector/hashmap/string you allocate that scales with n, (b) the maximum recursion depth (each frame ≈ O(1) unless it stores its own array), (c) output storage only if the problem asks for "extra" space excluding the required output.
    08 · Core skill

    Amortized analysis

    Some operations are usually cheap but occasionally expensive — and the trick is to prove the average cost over a sequence of operations is still low, even though any single call could be slow.

    dynamic_array.cppO(1) amortized
    std::vector<int> v;
for (int i = 0; i < n; i++)
    v.push_back(i); // usually O(1); occasionally O(k) to resize+copy

    std::vector::push_back is usually O(1). But when the backing array is full, it must allocate a bigger block (typically double the size) and copy every existing element — an O(k) operation. Because doubling means resizes happen at sizes 1, 2, 4, 8, 16, ..., the total copying cost across n pushes sums to 1+2+4+...+n ≈ 2n, which spread across n calls averages out to O(1) per call — this is amortized O(1), distinct from every call actually being fast.

    Say this in interviews"Amortized" is not "average case" — average case is about input distribution; amortized is a worst‑case guarantee over a sequence of operations, regardless of input.
    09 · Core skill

    Best, worst, and average case

    The same algorithm can have different complexities depending on the input arrangement, not just its size.

    linear_search.cpp
    int linearSearch(std::vector<int>& a, int target) {
    for (int i = 0; i < a.size(); i++)
        if (a[i] == target) return i;
    return -1;
}
    CaseScenarioComplexity
    BestTarget is the first elementO(1)
    AverageTarget is somewhere in the middle, uniformly randomO(n)
    WorstTarget is last, or absent entirelyO(n)

    Quicksort is the canonical example that trips people up: average case O(n log n) with a random or well‑chosen pivot, but worst case O(n²) if the pivot is repeatedly the smallest or largest element (e.g. an already‑sorted array with a naive "always pick first element" pivot strategy). Unless told otherwise, interviewers expect the worst case when they ask "what's the time complexity" with no qualifier.

    10 · Apply it

    The 6-step method: reading any code cold

    This is the actual procedure to run in your head when an interviewer hands you a function and says "what's the complexity?" — in order.

  • Identify the input(s) and name their sizes

    Is there one array of size n? Two of sizes n and m? A number n itself (careful — complexity for numeric inputs is often measured in bits, e.g. checking primality). Name every independent size variable.

  • Find every loop and recursive call, and classify its step

    Additive step (i++, i += k) → linear contribution. Multiplicative step (i *= 2) → logarithmic contribution. Recursive call shrinking input by a fraction → logarithmic or divide‑and‑conquer.

  • Determine nesting vs. sequencing

    Are loops/recursive structures inside one another (multiply their costs) or one after another (add their costs)? Draw imaginary boxes around each loop to see the nesting depth clearly.

  • Check if inner bounds depend on the outer variable

    If an inner loop's range depends on the outer loop's current index (j = i or j < n - i), it's a triangular/shrinking pattern — still polynomial, but compute the actual sum (often still simplifies to the same order, just half the constant).

  • For recursion, write the recurrence relation and solve it

    Count subproblems (a), the shrink factor (b), and non‑recursive work per call (O(n^d)). Apply the Master Theorem or match one of the three memorized shapes from Section 6.3.

  • Combine, then apply the simplification rules

    Add the sequential pieces, multiply the nested pieces, then drop constants and lower‑order terms to land on the final Big‑O. Separately repeat the whole process counting memory allocated (not steps taken) to get the space complexity.

    • Common traps interviewers plant • A loop that looks like it runs n times but actually breaks early or is bounded by a small constant (e.g. looping over a fixed‑size alphabet of 26 letters is O(1), not O(n)).
    • Built‑in function calls that hide complexity — std::string::substr is O(k) (copies), std::vector::erase(begin()) is O(n) (shifts everything), unordered_map lookups are O(1) average but O(n) worst case (hash collisions), std::sort is O(n log n).
    • Recursion that looks like it branches but actually only recurses down one path most of the time (e.g. memoized recursion, or one branch that returns immediately).

    Worked example — walk the method live

    worked_example.cpp
    bool hasPairWithSum(std::vector<int>& a, int target) {
    std::unordered_set<int> seen;           // step 1: input is array size n
    for (int x : a) {                    // step 2: single additive loop → n iterations
        if (seen.count(target - x)) return true; // O(1) avg hashset lookup
        seen.insert(x);                     // O(1) avg insert
    }
    return false;
}

    Walkthrough: one input, size n (step 1). One loop, additive step, not nested inside anything (steps 2–3). No inner-bound dependency, no recursion (steps 4–5). Loop body does O(1) average hash‑set work, run n times → O(n) time overall (step 6). Space: the seen set can hold up to n elements → O(n) time  O(n) space. This is the classic "trade space for time" upgrade over the O(n²) brute‑force nested‑loop pair check.

    12 · Apply it

    Practice questions

    State the time and (where relevant) space complexity before expanding each answer. Difficulty increases as you go.

    Q1Single pass over an array› 
    int maxVal(std::vector<int>& a) {
    int m = a[0];
    for (int x : a) m = std::max(m, x);
    return m;
}
    O(n) time O(1) space
    One loop over n elements, one variable for extra state.
    Q2Two separate loops› 
    void printBoth(std::vector<int>& a, std::vector<int>& b) {
    for (int x : a) std::cout << x;
    for (int y : b) std::cout << y;
}
    O(n + m) time O(1) space
    Sequential loops over two different inputs add — don't collapse to O(n) unless told n = m.
    Q3Nested loop, inner bound is constant› 
    void f(std::vector<int>& a) {
    for (int i = 0; i < a.size(); i++)
        for (int j = 0; j < 26; j++)
            doWork(a[i], j);
}
    O(n) time O(1) space
    The inner loop always runs exactly 26 times regardless of n — that's a constant, not a variable. O(26n) = O(n). Watch for fixed bounds disguised as loops (common with alphabets, digits, or a fixed board size).
    Q4Triangular nested loop› 
    void f(int n) {
    for (int i = 0; i < n; i++)
        for (int j = 0; j < i; j++)
            doWork();
}
    O(n²) time O(1) space
    Sum of 0+1+2+...+(n-1) = n(n-1)/2 → O(n²) after dropping constants and lower-order terms.
    Q5Three sequential nested-loop blocks› 
    void f(int n) {
    for (int i = 0; i < n; i++)
        doWork();                              // O(n)
    for (int i = 0; i < n; i++)
        for (int j = 0; j < n; j++)
            doWork();                          // O(n^2)
}
    O(n²) time
    O(n) + O(n²) — when adding, the largest term wins (rule #2). Total is O(n²), not O(n³) — they are not nested inside each other.
    Q6While loop with multiplicative shrink› 
    int countDigits(int n) {
    int count = 0;
    while (n > 0) { n /= 10; count++; }
    return count;
}
    O(log n) time O(1) space
    n shrinks by a factor of 10 each time — logarithmic (base 10, but log base doesn't matter for Big-O since it's a constant factor: log₁₀n = log₂n / log₂10).
    Q7Recursive Fibonacci with memoization› 
    std::unordered_map<int,int> memo;
int fib(int n) {
    if (n <= 1) return n;
    if (memo.count(n)) return memo[n];
    return memo[n] = fib(n-1) + fib(n-2);
}
    O(n) time O(n) space
    Each value 0..n is computed exactly once and cached — n unique subproblems, O(1) work each. Space: memo table O(n) plus recursion stack depth O(n).
    Q8Nested loop over two different arrays› 
    bool hasCommon(std::vector<int>& a, std::vector<int>& b) {
    for (int x : a)
        for (int y : b)
            if (x == y) return true;
    return false;
}
    O(n·m) time O(1) space
    Nested loops over different-sized inputs multiply their sizes: O(n) × O(m). Could be improved to O(n+m) using a hash set.
    Q9Recursive binary search› 
    int bs(std::vector<int>& a, int lo, int hi, int target) {
    if (lo > hi) return -1;
    int mid = lo + (hi - lo) / 2;
    if (a[mid] == target) return mid;
    if (a[mid] < target) return bs(a, mid+1, hi, target);
    return bs(a, lo, mid-1, target);
}
    O(log n) time O(log n) space
    T(n) = T(n/2) + O(1) → O(log n) time. Space is O(log n) here (not O(1)!) because each recursive call adds a stack frame — the iterative version from Section 4.6 is the O(1)-space alternative.
    Q10Generating all subsets› 
    void subsets(std::vector<int>& a, int i, std::vector<int>& cur) {
    if (i == a.size()) { process(cur); return; }
    subsets(a, i+1, cur);           // exclude a[i]
    cur.push_back(a[i]);
    subsets(a, i+1, cur);           // include a[i]
    cur.pop_back();
}
    O(2ⁿ) time O(n) space
    Two recursive calls per level, n levels deep → 2ⁿ total calls (one per subset — there really are 2ⁿ subsets, so this is optimal). Space is only O(n) for the recursion depth + current subset, since we don't store all subsets simultaneously here.
    Q11String concatenation in a loop› 
    std::string build(int n) {
    std::string s = "";
    for (int i = 0; i < n; i++)
        s += "x";         // each += may copy the whole string
    return s;
}
    O(n²) time (worst case) O(n) space
    Each += can be O(current length) in the worst case (though std::string uses amortized-doubling growth internally similar to vector, so in practice it's closer to amortized O(n) total — but treat naive repeated concatenation as the classic O(n²) trap unless the language/structure guarantees amortized growth). Compare with std::ostringstream or reserving capacity upfront.
    Q12Matrix traversal› 
    int sumMatrix(std::vector<std::vector<int>>& m) {
    int total = 0;
    for (auto& row : m)
        for (int x : row)
            total += x;
    return total;
}
    O(r·c) time O(1) space
    With r rows and c columns this visits every cell exactly once — O(r·c). If it's a square matrix (r = c = n), this is commonly written O(n²), but don't assume square unless stated.
    Q13Two-pointer technique› 
    bool isPalindrome(std::string& s) {
    int l = 0, r = s.size() - 1;
    while (l < r) {
        if (s[l] != s[r]) return false;
        l++; r--;
    }
    return true;
}
    O(n) time O(1) space
    Looks like it "loops" but two pointers moving toward each other still only visit each index once combined — n/2 iterations, still O(n). This is the two-pointer pattern: despite feeling clever, it's linear, not logarithmic — don't confuse "pointers converging" with "halving".
    Q14Sliding window› 
    int maxSumWindow(std::vector<int>& a, int k) {
    int windowSum = 0, best = 0;
    for (int i = 0; i < a.size(); i++) {
        windowSum += a[i];
        if (i >= k) windowSum -= a[i - k];
        if (i >= k - 1) best = std::max(best, windowSum);
    }
    return best;
}
    O(n) time O(1) space
    Despite involving a "window" of size k, each element is added once and removed once — total work is 2n, still O(n). This beats the naive nested-loop O(n·k) approach of resumming every window from scratch.
    Q15Recursive tree traversal› 
    struct Node { int val; Node *left, *right; };
int height(Node* root) {
    if (!root) return 0;
    return 1 + std::max(height(root->left), height(root->right));
}
    O(n) time
    Visits every node in the tree exactly once (n nodes total) → O(n) time. Space is O(h) where h is tree height — O(log n) for a balanced tree, but O(n) worst case for a completely skewed (linked-list-shaped) tree. Always state space in terms of height, and mention the skewed worst case.
    Q16Function with an early return› 
    bool containsDuplicate(std::vector<int>& a) {
    std::unordered_set<int> seen;
    for (int x : a) {
        if (seen.count(x)) return true; // might exit on iteration 1
        seen.insert(x);
    }
    return false;
}
    Best: O(1) · Worst: O(n)
    Interviewers want the worst case by default: O(n) time, O(n) space (the seen set can hold up to n elements before returning false).
    Q17Nested loop where the inner loop is logarithmic› 
    void f(int n) {
    for (int i = 0; i < n; i++)
        for (int j = 1; j < n; j *= 2)
            doWork();
}
    O(n log n) time
    Outer loop is O(n), inner loop is O(log n), and they're nested (multiply) → O(n log n). This exact pattern shows up in algorithms like building a sparse table or certain binary-indexed-tree operations.
    Q18Full permutation generation› 
    void permute(std::vector<int>& a, int k) {
    if (k == a.size()) { process(a); return; }
    for (int i = k; i < a.size(); i++) {
        std::swap(a[k], a[i]);
        permute(a, k + 1);
        std::swap(a[k], a[i]); // backtrack
    }
}
    O(n!) time O(n) space
    Generates all n! permutations, and at each of the n levels of recursion does O(n) work in the loop, so more precisely it's O(n · n!) — but the dominant, commonly-quoted term is O(n!). Space is O(n) for the recursion depth (permutations are built in-place via swaps, not stored separately).
