Why systems need rate limiting

Three reasons this comes up in almost every system design interview:

Protect

Shields backends and databases from traffic spikes, retries storms, and denial-of-service style abuse.

Fair share

Stops one noisy client from starving capacity that other tenants or users depend on.

Cost control

Caps spend on metered downstream calls — third-party APIs, LLM tokens, SMS, compute.

The five algorithms

Every interview answer comes down to one of these. Know the mechanism, the trade-off, and one real system that uses it.

Token Bucket

O(1) memory per key
  1. Each key (user, IP, API key) owns a bucket holding up to capacity tokens.
  2. Tokens refill continuously at a fixed rate, up to the capacity ceiling.
  3. A request consumes one token if available and proceeds; otherwise it's rejected (or queued).

Pros

  • Allows short bursts up to capacity — good UX
  • Cheap: one counter + timestamp per key
  • Simple to reason about and tune

Cons

  • Burst can still momentarily exceed the "average" rate
  • Two knobs to tune (capacity, refill rate)

Used by: AWS API Gateway, Stripe API.

Leaky Bucket

O(1) memory per key
  1. Incoming requests join a fixed-size queue (the "bucket").
  2. Requests are processed — "leaked" — at a constant fixed rate, regardless of arrival rate.
  3. If the queue is full when a request arrives, it's dropped.

Pros

  • Output rate is perfectly smooth — great for protecting downstream systems
  • Predictable processing rate

Cons

  • Adds queueing latency, even for isolated requests
  • Bursts get delayed, not admitted — worse UX than token bucket

Used by: network traffic shaping, some payment processors.

leaks out at fixed rate

Fixed Window Counter

O(1) memory per key
  1. Time is split into fixed windows (e.g. every 60s wall-clock minute).
  2. A counter increments per request within the current window.
  3. If the counter exceeds the limit, reject; the counter resets to zero at the window boundary.

Pros

  • Trivially simple — one counter + expiry per key
  • Very cheap, easy to implement with Redis INCR + EXPIRE

Cons

  • Boundary burst: up to 2× the limit can slip through across a window edge
  • Not smooth — bursty by construction

Used by: simple API quota systems, coarse-grained throttles.

Sliding Window Log

O(n) memory — n = requests in window
  1. Store the timestamp of every request per key (e.g. a Redis sorted set).
  2. On a new request, evict timestamps older than now − window.
  3. If the remaining count is below the limit, allow and record the new timestamp.

Pros

  • Perfectly accurate — no boundary bug
  • Window slides continuously, not in discrete steps

Cons

  • Memory scales with request volume, not just key count
  • Costlier at high throughput — pruning on every request

Used by: precise per-user throttles at moderate traffic.

Sliding Window Counter

O(1) memory per key
  1. Keep two fixed-window counters: the current window and the previous one.
  2. Estimate the sliding count as a weighted blend: prev_count × overlap% + curr_count.
  3. Allow the request if the estimate is under the limit.

Pros

  • Smooths the fixed-window boundary problem cheaply
  • Still just two counters — O(1) memory

Cons

  • Approximate, not exact (assumes uniform distribution within the window)
  • Slightly more logic than plain fixed window

Used by: Cloudflare, many API gateways — the practical default.

Distributed rate limiting

The core problem

  • With multiple app servers, in-memory counters per instance don't share state — a client could get N× the limit by hitting N servers.
  • Solution: a shared, fast store (typically Redis) holding the counter or token bucket per key.

Making it correct & fast

  • Use atomic ops (INCR + EXPIRE) or a Lua script to avoid check-then-increment race conditions.
  • For very high scale, layer a coarse local limiter in front of a stricter global Redis-backed one.
  • Shard by key (hash the user/IP to a Redis node) so no single node becomes a hotspot.

The HTTP contract

A rate limiter should communicate its state, not just fail silently.

HTTP/1.1 429 Too Many Requests
X-RateLimit-Limit:     100
X-RateLimit-Remaining: 0
X-RateLimit-Reset:     1735689600
Retry-After:           42

Token bucket when you want to allow natural bursts (e.g. a user loading a dashboard that fires several calls at once) with cheap O(1) state. Sliding window (log or counter) when you need tighter guarantees against burst-at-the-edge abuse and can afford slightly more memory or a small accuracy trade-off. In practice: token bucket for client-facing APIs, sliding window counter for abuse/security throttles.
Move the counter out of process into a shared store like Redis, and make the check-and-increment atomic (Lua script or Redis's built-in atomic commands) so concurrent requests from different servers can't race past the limit. For scale, add a local, slightly looser limiter per server as a first-line filter to cut Redis load, backed by the authoritative global limiter.
Depends on the threat model. IP-based limiting is the first line of defense against anonymous abuse but breaks down behind NAT or shared proxies. User/API-key-based limiting is fairer and more precise for authenticated traffic. Many production systems layer both: a loose IP limit plus a tighter per-account limit.
Sharded Redis (or a purpose-built store) holding a token bucket per API key, checked via an atomic Lua script at the edge/gateway layer before the request reaches backend services. Add tiered limits (per-second burst + per-day quota), return 429 with Retry-After, and keep a local in-memory fallback limiter for when Redis is briefly unavailable, so the system fails safe rather than open.
Because the window resets sharply at a clock boundary, a client can send the full limit right at the end of one window and again right at the start of the next — up to 2× the intended rate in a short span. Fix it with a sliding window counter (weight the previous window by overlap) or a full sliding log for exact correctness.
Local is fast and has zero network cost but is per-instance, so the effective limit multiplies with server count and resets on deploys. Centralized is accurate and consistent across the fleet but adds a network hop and a dependency whose failure needs a fallback plan. Most real systems use local as a cheap first filter and centralized as the source of truth.
