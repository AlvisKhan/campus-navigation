Everything they'll ask about RAG

A compressed reference for interview prep — the pipeline, the trade-offs, the terms that get dropped in casually, and the questions that actually get asked. Expand any panel for depth; skip it for the fast pass.

RAG = give an LLM an external, searchable knowledge source at inference time, so it answers using retrieved evidence instead of only what it memorized during training.
01

What problem RAG solves

mark reviewed

Three LLM limitations, one fix each:

Stale knowledge

Model weights are frozen at training time. RAG injects current or private facts without retraining.

Hallucination

Grounding generation in retrieved passages gives the model something real to cite instead of guessing.

No source of truth

Answers can point back to the exact document/chunk they came from — auditable, unlike parametric memory.

RAG vs. fine-tuning — when to pick which
RAGFine-tuning
Best forFast-changing or proprietary factsTeaching a style, format, or skill
Update costRe-index a document (cheap)Retrain (expensive)
TraceabilityHigh — cite the source chunkLow — baked into weights
Failure modeBad retrieval → bad answerOverfitting / catastrophic forgetting

Interview line: "they're not mutually exclusive — fine-tune the model to follow instructions and use tools well, RAG to keep it factually current."

02

The pipeline, end to end

mark reviewed

Two phases: indexing (offline, done once per document) and query time (online, done per user question).

fig.1 — indexing builds the index once; every query re-runs the bottom row only.
What each stage actually does under the hood
  • Chunking — splits documents into passages small enough to embed meaningfully and fit in the context window, large enough to keep coherent meaning.
  • Embedding — a bi-encoder maps text to a dense vector where semantic similarity ≈ vector closeness (cosine / dot product).
  • Vector store — indexes vectors for approximate nearest-neighbor (ANN) search at scale (HNSW, IVF, etc.) instead of brute-force comparison.
  • Retrieval — embeds the query with the same model, pulls the top-k nearest chunks.
  • Reranking — a slower, more accurate cross-encoder re-scores the top-k against the query for precision (optional but common in production).
  • Augmentation — retrieved chunks get inserted into the prompt template alongside the user query and instructions.
  • Generation — the LLM produces the final answer conditioned on that context.
03

Chunking strategy

mark reviewed

The highest-leverage, most-underrated design decision in a RAG system.

fig.2 — overlap between neighboring chunks prevents an answer-bearing sentence from being severed at a boundary.

Fixed-size

Split every N tokens/characters, with overlap. Simple, fast, ignores structure — can cut a sentence in half.

Recursive / structure-aware

Split on paragraph → sentence → word boundaries in order, only falling back to a smaller unit when needed. The default in most frameworks.

Semantic chunking

Split where embedding similarity between adjacent sentences drops — keeps topically coherent chunks, costs extra compute.

Parent-child (small-to-big)

Embed small chunks for precise retrieval, but return the larger parent chunk to the LLM for full context. Best of both worlds.

Interview trap — "bigger chunks = better answers." False: bigger chunks dilute the embedding (topic drift) and blow the context budget. The real lever is matching chunk size to query granularity.
04

Retrieval methods

mark reviewed

Sparse and dense retrieval fail in complementary ways — hybrid search exists to cancel out each one's blind spot.

Sparse (BM25 / TF-IDF)

Keyword / term-frequency matching. Great at exact terms, IDs, acronyms, rare words. Blind to synonyms and paraphrase.

Dense (embeddings)

Semantic vector similarity. Great at paraphrase and meaning. Can miss exact codes, numbers, or unusual proper nouns it wasn't trained to represent well.

fig.3 — hybrid search: run both, merge ranked lists with Reciprocal Rank Fusion (RRF), then optionally rerank.
Reranking — why bother if retrieval already ranks results?

The retriever (bi-encoder) embeds query and document independently for speed — it has to, to search millions of vectors fast. A reranker (cross-encoder) looks at the query and each candidate document together, so it captures interaction between them and is far more accurate — but too slow to run over the whole corpus. Standard pattern: retrieve top 50–100 cheaply, rerank down to top 3–5 precisely.

05

Advanced RAG techniques

mark reviewed

Namedrop-worthy patterns interviewers use to probe whether you've gone past a tutorial.

Query rewriting / expansion
Rewrite or expand the raw user query before embedding it — fixes ambiguous, underspecified, or conversational queries ("what about the second one?") so retrieval has something concrete to match against.
HyDE (Hypothetical Document Embeddings)
Ask the LLM to write a hypothetical answer to the query first, then embed that instead of the raw query. A fake answer is often closer in embedding space to a real answer-bearing chunk than the terse question is.
Multi-query retrieval
Generate several paraphrased versions of the query, retrieve for each, and union/dedupe the results. Reduces the risk that one phrasing misses the relevant chunk.
Self-RAG / Corrective RAG (CRAG)
The model critiques its own retrieved context before generating — grading relevance, deciding whether to retrieve again, fall back to web search, or answer without retrieval at all. Adds a control loop on top of the basic pipeline.
Graph RAG
Build a knowledge graph (entities + relations) alongside or instead of a vector index. Better for multi-hop questions ("who reports to the person who approved X?") that pure similarity search handles poorly.
Agentic RAG
The model decides if, when, and what to retrieve as a tool call mid-reasoning, possibly across multiple retrieval steps, rather than a single fixed retrieve-then-generate pass.
06

Evaluation

mark reviewed

Evaluate retrieval and generation separately — a bad final answer could be either stage's fault.

fig.4 — the RAGAS-style split: diagnose which half of the pipeline is actually broken.
MetricMeasuresStage
Context precisionOf retrieved chunks, how many are actually relevant?Retrieval
Context recallOf all relevant chunks that exist, how many were retrieved?Retrieval
FaithfulnessIs the answer supported by the retrieved context, or is it hallucinating beyond it?Generation
Answer relevancyDoes the answer actually address the question asked?Generation

Common frameworks to name-drop: RAGAS, TruLens, DeepEval. All lean heavily on an LLM-as-judge for faithfulness/relevancy since there's no clean ground truth.

Classic gotcha — the embedding model used at query time must match (or be compatible with) the one used at indexing time. Swapping embedding models silently breaks retrieval until you re-index everything.
08

Rapid recall — flip to check

mark reviewed

Click a card to reveal the answer. Good for a last-pass drill before the interview.

QWhy chunk documents instead of embedding whole files?

Embeddings degrade at capturing fine-grained meaning over long text (topic dilution), and most encoders have a token limit. Smaller chunks give more precise, addressable retrieval units.

QBi-encoder vs. cross-encoder — what's the difference?

Bi-encoder embeds query/doc separately (fast, scalable, used for retrieval). Cross-encoder scores query+doc jointly (slow, accurate, used for reranking a small candidate set).

QWhat is RRF?

Reciprocal Rank Fusion — merges multiple ranked lists (e.g. sparse + dense) by scoring each doc as the sum of 1/(k+rank) across lists, without needing comparable raw scores.

QName two causes of hallucination even with RAG.

1) Retrieval returns irrelevant/no chunks and the model fills the gap anyway. 2) The model ignores correct retrieved context and answers from parametric memory instead.

QWhat does "top-k" control, and what's the trade-off?

Number of chunks retrieved. Higher k = more recall but more noise, higher cost, and risk of exceeding/diluting the context window.

QWhen would you choose Graph RAG over vector RAG?

Multi-hop, relational questions (who → connected to → what) where similarity search over isolated chunks can't traverse relationships between entities.

QWhat is "lost in the middle"?

LLMs attend more strongly to information at the start and end of a long context window, and are more likely to miss relevant facts placed in the middle.

QHow do you evaluate RAG without labeled ground truth?

Use an LLM-as-judge to score faithfulness (grounded in context?) and relevancy (answers the question?), often synthesized against a small hand-curated eval set.

QWhy re-embed the query with the same model used for documents?

Vector similarity is only meaningful within the same embedding space — mismatched models place query and document vectors in incomparable geometries.
