DBMS Overview

A Database Management System (DBMS) is software that manages a collection of interrelated data and provides controlled access to that data. It acts as an interface between the database and its end users or application programs.

Why DBMS over File Systems?

Data Redundancy
File systems duplicate data across files; DBMS minimizes redundancy via controlled storage.
Data Inconsistency
DBMS maintains consistency through integrity constraints and transactions.
Data Independence
Changes in physical storage don't affect application programs (logical/physical independence).
Concurrent Access
DBMS handles multiple users accessing data simultaneously without conflicts.
Security
Access control and authorization are built-in features.
Recovery
DBMS provides crash recovery through logs and backup mechanisms.

Three-Schema Architecture

Figure: ANSI/SPARC Three-Schema Architecture

Data Independence

  • Logical Data Independence: Ability to change the conceptual schema without changing external schemas or application programs.
  • Physical Data Independence: Ability to change the internal schema without changing the conceptual schema (or external schemas).

1. Entity-Relationship (ER) Model

The ER model is a conceptual data model used to describe the structure of a database. It was proposed by Peter Chen in 1976.

Basic Components

Entity
A real-world object that has an independent existence. Represented by a rectangle.
E.g., Student, Employee, Book
Attribute
A property of an entity. Represented by an ellipse.
E.g., Name, Age, Salary
Relationship
An association among entities. Represented by a diamond.
E.g., Works-in, Enrolled-in

Types of Attributes

TypeDescriptionSymbolExample
SimpleCannot be divided furtherEllipseAge, Salary
CompositeCan be divided into sub-attributesEllipse with sub-ellipsesName → (First, Last)
Multi-valuedCan have multiple valuesDouble ellipsePhone numbers
DerivedDerived from another attributeDashed ellipseAge (from DoB)
KeyUniquely identifies an entityUnderlined ellipseStudent_ID
NullMay have no value—Middle name

ER Diagram — Example

Figure: ER diagram — Student and Course with M:N Enrolled relationship

Types of Entities

  • Strong Entity: Has a primary key (own identifier). Drawn as a single rectangle.
  • Weak Entity: Does not have a primary key; depends on a strong entity. Drawn as a double rectangle. Its partial key is called a discriminator (dashed underline). The relationship between weak and strong entity is called an identifying relationship (double diamond).
🔶 Example — Weak Entity

Consider Employee (strong) and Dependent (weak). A dependent is identified by their name along with the employee they belong to. Dependant_Name is the discriminator. The composite key is (Employee_ID, Dependent_Name).

Cardinality (Participation) Constraints

CardinalityMeaningExample
1 : 1Each entity in A associates with at most 1 in B, vice versaPerson ↔ Passport
1 : NOne entity in A can relate to many in BDepartment → Employees
M : NMany entities in A can relate to many in BStudent ↔ Course

Participation constraints:

  • Total Participation (double line): Every entity MUST participate in the relationship.
  • Partial Participation (single line): An entity may or may not participate.

Generalization, Specialization & Aggregation

  • Specialization (top-down): A higher-level entity is divided into lower-level sub-entities. E.g., Employee is specialized into Engineer and Manager.
  • Generalization (bottom-up): Two lower-level entities are combined into a higher-level entity. E.g., Car and Bus → Vehicle.
  • Aggregation: A relationship set treated as a higher-level entity, so that it can participate in another relationship. Used when a relationship itself needs to have a relationship with another entity.
🎯 GATE PYQ — GATE 2014

Consider the following ER diagram. Which of the following is TRUE about the given ER diagram?
A weak entity set W is related to a strong entity set S via relationship R. W has a partial key attribute P.

  • (A) The primary key of W is a combination of P and the primary key of S
  • (B) P alone can serve as the primary key of W
  • (C) W cannot have any attributes of its own
  • (D) S must have at least two attributes
Answer: (A)
A weak entity does not have its own primary key. Its identifier (called a discriminator or partial key) combined with the primary key of its identifying strong entity forms its composite primary key.
🎯 GATE PYQ — GATE 2019

Consider an ER model with a relationship R between entities A and B. Participation of A in R is total and cardinality of R is M:N. Which of the following is TRUE?

  • (A) Every B must participate in R
  • (B) Every A must participate in R
  • (C) For every A, there is exactly one B
  • (D) For every B, there are exactly N values of A
Answer: (B)
Total participation of A in R means every entity of type A must participate in at least one instance of R. M:N cardinality means an A can relate to many B's and vice versa, but says nothing about mandatory participation of B.

2. Relational Model

The relational model, proposed by E.F. Codd in 1970, represents a database as a collection of relations (tables).

Key Terminology

Relation (Table)
A two-dimensional table with rows and columns.
Tuple (Row)
A single record in a relation. A relation with n tuples has n rows.
Attribute (Column)
A property/characteristic of a relation.
Domain
The set of permitted values for an attribute.
Schema
The structural description of a relation: R(A1, A2, ..., An)
Degree
Number of attributes (columns) in a relation.
Cardinality
Number of tuples (rows) in a relation.
NULL
Represents unknown or missing value. Not equal to 0 or empty string.

Types of Keys

Key TypeDefinitionKey Property
Super KeyAny set of attributes that uniquely identifies a tupleUnique identification (may have extra attributes)
Candidate KeyMinimal super key — no subset can uniquely identifyUnique + Minimal
Primary KeySelected candidate key used to identify tuplesUnique + Not NULL
Alternate KeyCandidate keys not chosen as primary key—
Foreign KeyAttribute referencing the primary key of another relationReferential Integrity
Composite KeyKey consisting of two or more attributesCombined uniqueness
🔶 Example — Identifying Keys

Consider relation: Student(RollNo, Name, Email, PhoneNo)

  • Super Keys: {RollNo}, {Email}, {PhoneNo}, {RollNo, Name}, {RollNo, Email}, ... (many)
  • Candidate Keys: {RollNo}, {Email}, {PhoneNo} — all minimal
  • Primary Key: {RollNo} (chosen)
  • Alternate Keys: {Email}, {PhoneNo}

How many super keys are there if candidate key is {A}?
If relation has n attributes and one candidate key {A}, then super keys = 2n−1 (A must be included, rest are optional).

⚠️
Common GATE trap: A super key does NOT have to be minimal. Every candidate key is a super key, but not every super key is a candidate key. The number of super keys = 2(n − |CK|) where |CK| is size of the minimal candidate key and n is total attributes.

Integrity Constraints

  • Domain Constraint: Each attribute value must come from the attribute's domain.
  • Entity Integrity: Primary key cannot be NULL.
  • Referential Integrity: A foreign key value must either be NULL or must match a primary key value in the referenced relation.
  • Key Constraint: No two tuples can have the same value for the primary key.
🎯 GATE PYQ — GATE 2015

Consider the relation R(A, B, C, D, E) with the following functional dependencies:
AB → C, D → B, and E → A.
Which of the following is a candidate key of R?

  • (A) ABD
  • (B) DE
  • (C) ADE
  • (D) ABE
Answer: (B) DE
Closure of DE:
Start: {D, E}
E → A, so add A: {D, E, A}
D → B, so add B: {D, E, A, B}
AB → C, so add C: {D, E, A, B, C}
DE+ = {A, B, C, D, E} = all attributes ✓
Check minimality: D+ = {D, B} ≠ all. E+ = {E, A} ≠ all. So DE is minimal → Candidate Key.

3. Relational Algebra & Tuple Calculus

Relational Algebra is a procedural query language that works on relations (tables). It forms the theoretical basis for SQL.

Fundamental Operations

Full Outer Join⟗—All tuples from both, NULLs where no match

Union Compatibility

Two relations R and S are union-compatible if:

  1. They have the same number of attributes (same degree).
  2. The domains of corresponding attributes are compatible.

Required for: Union (∪), Intersection (∩), Set Difference (−).

Worked Examples

🔶 Example — Selection and Projection

Given relation Employee(EmpID, Name, Dept, Salary):

  • "Find names of employees in the 'CS' department earning more than 50,000"
πName( σDept='CS' ∧ Salary>50000(Employee) )

Student(RollNo, Name, CourseID) and Course(CourseID, CourseName, Credits)

"Find student names and course names they are enrolled in:"

Natural join automatically joins on the common attribute CourseID.

🔶 Example — Division (÷)

R(Student, Course) and S(Course) where S contains all courses. Then R ÷ S gives students who are enrolled in every course in S.

R ÷ S = πStudent(R) − πStudent( πStudent(R) × S − R )

Result Size Estimation

📐
Important size formulas:
• |R × S| = |R| × |S| (Cartesian product)
• |R ∪ S| ≤ |R| + |S|
• |R ∩ S| ≤ min(|R|, |S|)
• |R − S| ≤ |R|
• |σc(R)| ≤ |R|
• |πA(R)| ≤ |R| (after removing duplicates)
• Natural join: 0 ≤ |R ⋈ S| ≤ |R| × |S|

Tuple Relational Calculus (TRC)

TRC is a non-procedural (declarative) query language. It uses variables that range over tuples.

A TRC query has the form: { t | P(t) } — the set of all tuples t satisfying predicate P(t).

🔶 TRC Example

"Find all employees with salary > 50,000":

{ t | t ∈ Employee ∧ t.Salary > 50000 }

"Find names of students enrolled in course C001":

{ t.Name | t ∈ Student ∧ ∃s(s ∈ Enrolled ∧ s.RollNo = t.RollNo ∧ s.CourseID = 'C001') }
🎯 GATE PYQ — GATE 2016

Let R(A, B) and S(B, C, D) be two relations. The number of tuples in R × S if |R| = m and |S| = n is:

  • (A) m + n
  • (B) m × n
  • (C) m − n
  • (D) m / n
Answer: (B) m × n
The Cartesian product of two relations produces every possible combination of tuples from both relations. So the total is m × n tuples.
🎯 GATE PYQ — GATE 2021

Consider relations R(A, B) with 3 tuples: {(1,2), (2,3), (4,5)} and S(B, C) with 4 tuples: {(2,6), (3,7), (5,8), (9,10)}. The number of tuples in R ⋈ S (natural join on B) is:

  • (A) 4
  • (B) 3
  • (C) 12
  • (D) 7
Answer: (B) 3
Match on B: R.B=2 matches S.B=2 → (1,2,6); R.B=3 matches S.B=3 → (2,3,7); R.B=5 matches S.B=5 → (4,5,8). So 3 tuples. Note: S has B=9 but no match in R.

4. SQL — Structured Query Language

SQL is the standard language for interacting with relational databases. It is both a DDL (Data Definition Language) and DML (Data Manipulation Language).

SQL Classification

DDL
CREATE, ALTER, DROP, TRUNCATE — defines schema structure
DML
SELECT, INSERT, UPDATE, DELETE — manipulates data
DCL
GRANT, REVOKE — controls access
TCL
COMMIT, ROLLBACK, SAVEPOINT — controls transactions

SELECT Statement Structure

SELECT   [DISTINCT] attribute_list
FROM     table_name(s)
[WHERE    condition]
[GROUP BY attribute(s)]
[HAVING   group_condition]
[ORDER BY attribute [ASC|DESC]];
📌
Order of execution (NOT the same as written order):
FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY

Aggregate Functions

FunctionReturnsIgnores NULLs?
COUNT(*)Total number of rowsNo
COUNT(A)Number of non-NULL values in AYes
SUM(A)Sum of all values in AYes
AVG(A)Average of non-NULL values in AYes
MAX(A)Maximum value in AYes
MIN(A)Minimum value in AYes

SQL Joins

Figure: SQL JOIN types

Subqueries

-- Correlated subquery: finds employees earning more than dept average
SELECT Name, Salary
FROM Employee E1
WHERE Salary > (
    SELECT AVG(Salary)
    FROM Employee E2
    WHERE E1.Dept = E2.Dept
);

GROUP BY vs HAVING

-- Count students per department, show only depts with >10 students
SELECT Dept, COUNT(*) AS StudentCount
FROM Student
GROUP BY Dept
HAVING COUNT(*) > 10
ORDER BY StudentCount DESC;
⚠️
HAVING vs WHERE: WHERE filters individual rows BEFORE grouping. HAVING filters groups AFTER GROUP BY. You cannot use aggregate functions in WHERE; use HAVING instead.

NULL Handling in SQL

  • Any comparison with NULL using =, <, > returns UNKNOWN (not TRUE or FALSE)
  • Use IS NULL or IS NOT NULL to check for NULL
  • In 3-valued logic: TRUE AND UNKNOWN = UNKNOWN, FALSE AND UNKNOWN = FALSE, TRUE OR UNKNOWN = TRUE
  • WHERE clause includes only rows where condition is TRUE (not UNKNOWN)
-- Wrong way to check NULL
SELECT * FROM Employee WHERE ManagerID = NULL;   -- Always returns 0 rows!

-- Correct way
SELECT * FROM Employee WHERE ManagerID IS NULL;
🎯 GATE PYQ — GATE 2017

Consider the following SQL query:
SELECT A, COUNT(B) FROM R GROUP BY A HAVING COUNT(B) > 1;
R has attributes A and B. The query returns tuples where:

  • (A) A has at least one NULL value
  • (B) A appears more than once in R (with non-NULL B)
  • (C) B has exactly one value per A
  • (D) A has no duplicates
Answer: (B)
GROUP BY A groups tuples by attribute A. COUNT(B) counts non-NULL values of B in each group. HAVING COUNT(B) > 1 means only groups where A appears more than once (with non-NULL B) are returned.
🎯 GATE PYQ — GATE 2022

Table T has columns P and Q. The query SELECT P, Q FROM T WHERE Q NOT IN (SELECT Q FROM T WHERE P='x') is equivalent to which relational algebra expression if T = {(a,1),(b,2),(x,2)}?

  • (A) {(a,1)} — only tuples where Q doesn't appear with P='x'
  • (B) {(a,1),(b,2)} — all non-x tuples
  • (C) {} — empty set
  • (D) {(a,1),(x,2)} — NULLs included
Answer: (A)
The inner query finds Q values where P='x': {2}. The outer query finds rows where Q NOT IN {2}: only (a,1) satisfies this since Q=1 not in {2}. Row (b,2) has Q=2 which IS in {2}, so excluded.

5. Functional Dependencies & Normalization

Normalization is the process of organizing a database to reduce redundancy and prevent anomalies (insertion, deletion, update).

Functional Dependency (FD)

An FD X → Y means: for any two tuples with the same X value, they must have the same Y value. "X functionally determines Y."

🔶 Example

In Student(RollNo, Name, DeptID, DeptName):
RollNo → Name, DeptID (knowing roll number determines name and department)
DeptID → DeptName (knowing department ID determines department name)

Armstrong's Axioms

These are sound and complete rules for deriving FDs:

AxiomRuleFormal Statement
ReflexivityA set always determines its subsetIf Y ⊆ X, then X → Y
AugmentationAdd attributes to both sidesIf X → Y, then XZ → YZ
TransitivityChain of dependenciesIf X → Y and Y → Z, then X → Z

Derived rules: Union (if X→Y and X→Z, then X→YZ), Decomposition (if X→YZ, then X→Y and X→Z), Pseudotransitivity.

Attribute Closure (X⁺)

The closure of a set of attributes X under a set F of FDs, written X+, is the set of all attributes that X can determine.

🔶 Computing Closure — Step by Step

R(A,B,C,D,E), FDs: {A→BC, B→D, CD→E}

Find A⁺:

  1. Start: X = {A}
  2. A → BC: add B, C → X = {A, B, C}
  3. B → D: add D → X = {A, B, C, D}
  4. CD → E: both C and D are in X, add E → X = {A, B, C, D, E}

A⁺ = {A, B, C, D, E} = all attributes, so A is a candidate key!

First Normal Form (1NF)

A relation is in 1NF if:

  • All attribute values are atomic (indivisible)
  • No repeating groups or multi-valued attributes in a single cell
  • Each row is unique
🔶 1NF Violation

Not 1NF: Student(RollNo, Name, Courses) where Courses = "Math, Physics, CS" (multi-valued)

Fixed (1NF): Create one row per course: Student(RollNo, Name, Course) with separate rows.

Second Normal Form (2NF)

A relation is in 2NF if it is in 1NF AND has no partial dependency — i.e., no non-prime attribute is dependent on a proper subset of any candidate key.

📌
Partial dependency only exists when the candidate key is composite (has multiple attributes). If CK is a single attribute, 2NF is automatically satisfied (given 1NF).
🔶 2NF Example

R(StudentID, CourseID, Grade, StudentName) — composite PK: {StudentID, CourseID}

FDs: StudentID,CourseID → Grade (full dependency ✓)
StudentID → StudentName (partial — only part of PK determines StudentName ✗)

Fix: Decompose into:

  • R1(StudentID, StudentName)
  • R2(StudentID, CourseID, Grade)

Third Normal Form (3NF)

A relation is in 3NF if it is in 2NF AND has no transitive dependency — no non-prime attribute depends on another non-prime attribute.

Formal definition: For every non-trivial FD X → Y, either:

  • X is a super key, OR
  • Y is a prime attribute (part of some candidate key)
🔶 3NF Example

R(StudentID, DeptID, DeptName)

FDs: StudentID → DeptID, DeptID → DeptName
Transitive: StudentID → DeptID → DeptName (DeptName depends on non-key DeptID ✗)

Fix: Decompose into:

  • R1(StudentID, DeptID)
  • R2(DeptID, DeptName)

Boyce-Codd Normal Form (BCNF)

A relation is in BCNF if for every non-trivial FD X → Y, X must be a super key.

BCNF is stronger than 3NF. Every BCNF relation is in 3NF, but not vice versa.

🔶 BCNF vs 3NF (Classic Example)

R(Student, Course, Instructor)
CKs: {Student, Course} and {Student, Instructor}
FDs: {Student,Course} → Instructor, {Student,Instructor} → Course, Instructor → Course

FD: Instructor → Course — LHS (Instructor) is NOT a super key, so NOT BCNF.
But is it 3NF? Course is a prime attribute (part of CK {Student,Course}), so the second condition of 3NF is satisfied → it IS in 3NF.

This relation is in 3NF but NOT in BCNF.

💡
3NF vs BCNF:
• 3NF always achieves lossless decomposition + dependency preservation
• BCNF always achieves lossless decomposition but may NOT preserve all dependencies
• When there is a conflict, prefer 3NF to maintain dependency preservation

Lossless Decomposition Test

Decomposition of R into R1 and R2 is lossless if and only if:

(R1 ∩ R2) → R1   OR   (R1 ∩ R2) → R2

i.e., the common attributes form a super key of at least one of the sub-relations.

🔶 Lossless Decomposition Test

R(A, B, C), FDs: A → B, B → C. Decompose into R1(A,B) and R2(B,C).

R1 ∩ R2 = {B}. Is B → A (super key of R1)? A,B are in R1, B determines C but does B → A? Check: B+ = {B,C}. B does not determine A. But does B → B,C (super key of R2)? R2 = (B,C) and B → C means B+ includes B,C = all of R2 → YES. So decomposition is lossless.

Canonical Cover (Fc)

A canonical cover is a minimal set of FDs equivalent to F, where:

  1. No FD in Fc has extraneous attributes (on either side)
  2. No FD in Fc is redundant (can be derived from others)
  3. Each FD's RHS is a single attribute
🎯 GATE PYQ — GATE 2018

Consider relation R(A, B, C, D) with FDs: A→B, BC→D, B→C. Which of the following is the canonical cover?

  • (A) {A→B, BC→D, B→C}
  • (B) {A→B, B→C, AB→D}
  • (C) {A→BC, B→C}
  • (D) {A→BCD}
Answer: (B)
In BC→D, since B→C, C is extraneous (B already determines C). So BC→D simplifies to B→D. But since A→B→D (transitivity), we check if B→D is redundant. Actually after removing C from LHS of BC→D, we get B→D. The canonical cover: {A→B, B→C, B→D} — but this depends on what's derivable. Checking option B: AB→D where A→B so A→D holds, minimal form is correct.
🎯 GATE PYQ — GATE 2020

Consider a relation R(A,B,C) with FDs: A→B, B→C, C→A. Which of the following is NOT correct?

  • (A) R is in BCNF
  • (B) R is in 3NF
  • (C) R has exactly one candidate key
  • (D) A, B, and C are all candidate keys
Answer: (C)
A+ = {A,B,C}, B+ = {B,C,A}, C+ = {C,A,B}. All three determine all attributes, so A, B, C are ALL candidate keys. R has THREE candidate keys, not one. Since every FD's LHS is a candidate key (= superkey), R is in BCNF.

Indexing Concepts

An index is a data structure that speeds up retrieval. It maps search key values to disk block addresses containing those records.

Primary Index
Index on the ordering key of a sequentially ordered file. One entry per block. Called sparse index.
Clustering Index
Index on a non-key ordering field. Multiple records per entry. Also sparse.
Secondary Index
Index on a non-ordering field. One entry per record. Called dense index.
Dense Index
One index entry for every search key value in the data file.
Sparse Index
Index entry only for some values (e.g., one per block).
Multi-level Index
Index on top of index to reduce search space further.

B-Tree

A B-tree of order m (max m children per node):

  • Every node has at most m children
  • Every node (except root) has at least ⌈m/2⌉ children
  • Root has at least 2 children (if not a leaf)
  • All leaves are at the same level
  • A node with k children contains k−1 keys
  • Data pointers exist in all nodes (both internal and leaf)

B+ Tree (More Common in GATE)

In a B+ tree of order p:

  • Data pointers exist ONLY in leaf nodes
  • Internal nodes store only routing keys for navigation
  • All leaf nodes are linked together (a linked list for range queries)
  • All keys appear in leaf nodes

Figure: B+ Tree structure — internal nodes for routing, leaf nodes contain data pointers and are linked

Key Formulas for B-Trees (GATE Numericals)

📐
B-Tree of order m (max m children):
• Max keys per node = m − 1
• Min keys per non-root node = ⌈m/2⌉ − 1
• Max entries = (mh+1 − 1)/(m−1) for height h

B+ Tree (internal node order p, leaf node order pL):
• Internal node: ⌈p/2⌉ ≤ children ≤ p
• Leaf node: ⌈pL/2⌉ ≤ entries ≤ pL
• Number of leaf nodes for n records: ⌈n / pL⌉
• Height h = ⌈log⌈p/2⌉(n)⌉
🔶 Numerical Example — B+ Tree

Block size = 512 bytes, search key size = 4 bytes, block pointer = 6 bytes, record pointer = 7 bytes. Find order p of B+ tree internal nodes.

Each internal node: p × 6 + (p−1) × 4 ≤ 512
6p + 4p − 4 ≤ 512
10p ≤ 516
p ≤ 51.6 → p = 51

For leaf nodes: pL × (4 + 7) + 6 ≤ 512
11 pL ≤ 506
pL ≤ 46 → pL = 46

🎯 GATE PYQ — GATE 2019

A B+ tree of order 3 (i.e., each node can have at most 3 children) is built for 13 distinct values. What is the minimum height of this tree (root at height 0)?

  • (A) 2
  • (B) 3
  • (C) 4
  • (D) 1
Answer: (B) 3
Order 3 → leaf nodes can hold ≤ 2 entries, internal nodes ≤ 3 children. Max entries at height h: at height 0 (only root leaf) = 2. At height 1: 2 leaves max (⌈3/2⌉=2 min children) × 2 entries each = 4. At height 2: 4×2=8. At height 3: 8×2=16. To store 13, minimum height is 3 (can hold up to 16 entries).

7. Transactions & ACID Properties

A transaction is a unit of program execution that accesses and possibly modifies various data items. It must either execute completely or not at all (all-or-nothing).

ACID Properties

⚛ Atomicity
Either ALL operations of a transaction complete, or NONE do. Ensured by the recovery manager (logs, undo).
✅ Consistency
A transaction takes the database from one consistent state to another. Ensured by the application programmer and integrity constraints.
🔒 Isolation
Concurrent transactions appear to execute serially. Ensured by concurrency control (locks, MVCC).
💾 Durability
Once a transaction commits, its effects persist even after a system crash. Ensured by the recovery manager (write-ahead logging).

Transaction States

Figure: Transaction state diagram

Schedules & Serializability

A schedule is a sequence of operations from multiple transactions. A schedule is serializable if its outcome equals that of some serial schedule (transactions run one after another with no interleaving).

Conflict Serializability

Two operations conflict if:

  1. They belong to different transactions
  2. They access the same data item
  3. At least one of them is a write operation

Conflicting pairs: R-W, W-R, W-W (NOT R-R)

Precedence (Serialization) Graph

To test conflict serializability:

  1. Create a node for each transaction Ti
  2. Draw edge Ti → Tj if an operation of Ti conflicts with a later operation of Tj
  3. If the graph has no cycle, the schedule is conflict serializable
  4. Topological sort of the graph gives the equivalent serial schedule
🔶 Conflict Serializability Example

Schedule S:

T₁
R(A)
W(A)
R(B)
Commit
T₂
R(A)
W(B)
Commit

Conflicts: T₁W(A) before T₂R(A) → T₁→T₂. T₂W(B) before T₁R(B) → T₂→T₁.

Cycle: T₁→T₂→T₁ ∴ NOT conflict serializable!

🔶 View Serializability

A schedule S is view serializable if it is view equivalent to a serial schedule. View equivalence requires:

  1. Initial Read: If Ti reads initial value of Q in S, same in S'
  2. Updated Read: If Ti reads value of Q written by Tj in S, same in S'
  3. Final Write: If Ti performs final write on Q in S, same in S'
📌
Every conflict serializable schedule is view serializable, but NOT vice versa. View serializability is a broader concept (includes some non-conflict-serializable schedules).
🎯 GATE PYQ — GATE 2016

Consider schedule:
T₁: R(X), R(Y), W(X)
T₂: R(X), W(X), W(Y)
Interleaved: R₁(X), R₂(X), W₂(X), W₂(Y), R₁(Y), W₁(X)
Is this conflict serializable?

  • (A) Yes, equivalent to T₁T₂
  • (B) No, not conflict serializable
  • (C) Yes, equivalent to T₂T₁
  • (D) Cannot determine
Answer: (B)
Conflicts: R₁(X) → W₂(X): T₁→T₂. W₂(X) → W₁(X): T₂→T₁. This creates a cycle T₁→T₂→T₁, so the schedule is NOT conflict serializable.

Lock-Based Protocols

Types of Locks

  • Shared Lock (S-lock / Read Lock): Multiple transactions can hold simultaneously. Used for reading.
  • Exclusive Lock (X-lock / Write Lock): Only one transaction can hold at a time. Used for writing. Incompatible with all other locks.
Lock CompatibilityS (held)X (held)
S (requested)✓ Compatible✗ Incompatible
X (requested)✗ Incompatible✗ Incompatible

Two-Phase Locking (2PL)

A transaction follows 2PL if it has two phases:

  1. Growing Phase: Locks are acquired; NO locks are released
  2. Shrinking Phase: Locks are released; NO new locks are acquired

The point where the last lock is acquired is the lock point.

Figure: Two-Phase Locking protocol — locks can only be acquired in growing phase, released in shrinking phase

Variants of 2PL

VariantRulePrevents
Basic 2PLStandard growing and shrinking phasesNon-serializable schedules
Strict 2PLHold all exclusive locks until after COMMIT/ABORTDirty reads, cascading rollback
Rigorous 2PLHold ALL locks until after COMMIT/ABORTAll anomalies (most restrictive)
Conservative 2PLAcquire ALL locks before transaction startsDeadlock (but may cause starvation)
⚠️
2PL Guarantees Conflict Serializability but does NOT prevent Deadlock. Strict 2PL and Rigorous 2PL also prevent cascading rollback (dirty reads). Conservative 2PL prevents deadlock but not always practical.

Deadlock

Deadlock occurs when each transaction in a set is waiting for another transaction in the set to release a lock.

Deadlock Detection

Maintain a Wait-For Graph (WFG): draw edge Ti → Tj if Ti is waiting for Tj to release a lock. If WFG has a cycle, deadlock exists. Resolve by rolling back (aborting) one transaction (the victim).

Deadlock Prevention

ProtocolStrategyApproach
Wait-DieNon-preemptive (older waits for younger; younger dies)Older T waits; younger T is rolled back
Wound-WaitPreemptive (older wounds younger; younger waits)Older T preempts younger; younger T waits for older
💡
Memory tip for Wait-Die vs Wound-Wait:
Wait-Die: Old waits, Young dies (the young transaction is aborted and restarted)
Wound-Wait: Old wounds (preempts) Young, Young waits (old transaction gets to proceed)

Timestamp-Based Concurrency Control

Each transaction Ti is given a timestamp TS(Ti) when it starts. Rules:

  • Thomas's Write Rule: If Ti wants to write Q but TS(Ti) < W-timestamp(Q), the write is ignored (not aborted!) — an even newer transaction has already written Q.
  • Read Rule: If TS(Ti) < W-timestamp(Q), Ti is rolled back (dirty read from a later transaction).

🎯 GATE PYQ — GATE 2018

Which one of the following is NOT a valid deadlock prevention scheme?

  • (A) Wait-Die
  • (B) Wound-Wait
  • (C) Wait-Wait
  • (D) Conservative 2PL (all locks at start)
Answer: (C) Wait-Wait
"Wait-Wait" is not a real protocol. In this scheme, all transactions just wait for each other, which leads directly to deadlock rather than preventing it. The valid protocols are Wait-Die, Wound-Wait, and pre-claiming all locks (Conservative 2PL).
🎯 GATE PYQ — GATE 2023

A schedule S consists of the following operations:
T₁: R(X), R(Y); T₂: W(X), W(Y). Schedule: R₁(X), W₂(X), R₁(Y), W₂(Y), commit T₂, commit T₁.
Which problem does this schedule illustrate?

  • (A) Non-repeatable read
  • (B) Dirty read
  • (C) Lost update
  • (D) Phantom read
Answer: (A) Non-repeatable read
T₁ reads X, then T₂ writes (updates) X and Y and commits. If T₁ were to read X again, it would get a different value. This is a non-repeatable read (also called fuzzy read) — same item read twice gives different values due to an intervening committed write.

Database Recovery Techniques

Recovery ensures that committed transactions are reflected in the database and uncommitted transactions are rolled back after a crash.

Log-Based Recovery

The system maintains a log file (write-ahead log / WAL) on stable storage. Before writing to the database, the log entry must be written first.

Log records: <Ti, start>, <Ti, X, old_val, new_val>, <Ti, commit>, <Ti, abort>

Undo vs Redo

UNDO
Roll back (undo) changes of an uncommitted transaction. Used for transactions that started but did NOT commit before crash.
REDO
Re-apply changes of a committed transaction. Used when transaction committed but changes may not have been written to disk.

Checkpointing

A checkpoint is a point where the system writes all modified buffer blocks to disk and writes a <checkpoint> record to the log. During recovery, transactions before the last checkpoint that committed do not need to be redone.

ARIES Recovery Algorithm

Three phases:

  1. Analysis Pass: Scan log forward from last checkpoint to find all committed and failed transactions.
  2. Redo Pass: Redo all changes from the first log entry that might not be on disk.
  3. Undo Pass: Undo changes of all failed transactions (in reverse log order).

Shadow Paging

Maintains two page tables: current and shadow. Transactions work on a copy; on commit, the shadow page table is updated to point to new pages. Simple but no concurrent transactions.

Quick Reference — Key Formulae

Super Keys

If a relation has n attributes and a candidate key of size k,
Number of super keys = 2n − k

Relational Algebra Result Sizes

|R × S| = |R| × |S|

0  ≤  |R ⋈ S|  ≤  |R| × |S|

If join on key: |R ⋈key S| ≤ min(|R|, |S|)

|σc(R)| = |R| / V(c, R)    [V = number of distinct values]

B-Tree (Order m)

Max keys per node: m − 1

Min keys per non-root node: ⌈m/2⌉ − 1

Max entries for height h:   (mh+1 − 1) / (m − 1)

Min entries for height h:   2 · ⌈m/2⌉h−1 − 1   (h ≥ 1)

B+ Tree Internal Node

p × Ppointer + (p − 1) × Vkey ≤ Block size

Solve for p (order of internal node)

B+ Tree Leaf Node

pL × (Vkey + Precord) + Ppointer ≤ Block size

Solve for pL (leaf order)

Lossless Join Condition

Decomposition R → R₁, R₂ is lossless iff

(R₁ ∩ R₂) → R₁    OR    (R₁ ∩ R₂) → R₂

BCNF Check

For every non-trivial FD X → Y in R:

X must be a superkey of R

3NF Check

For every non-trivial FD X → A in R:

X is a superkey of R    OR    A is a prime attribute

Timestamp Ordering Rules

Read(Q) by Ti:
  If TS(Ti) < W-TS(Q) → rollback Ti
  Else: read; R-TS(Q) = max(R-TS(Q), TS(Ti))

Write(Q) by Ti:
  If TS(Ti) < R-TS(Q) → rollback Ti
  If TS(Ti) < W-TS(Q) → ignore write (Thomas's rule)
  Else: write; W-TS(Q) = TS(Ti)
💡
Normal Forms Quick Summary:
• 1NF: Atomic values only
• 2NF: 1NF + No partial dependency (non-prime depends only on full CK)
• 3NF: 2NF + No transitive dependency (non-prime doesn't depend on non-prime)
• BCNF: 3NF + For every FD X→Y, X must be superkey
• 4NF: BCNF + No non-trivial multi-valued dependencies
